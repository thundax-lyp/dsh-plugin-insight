# 研究输出标准

本标准适用于首轮研究、后续整轮研究、同轮断点恢复与独立单插件洞察。
列表编排 Skill 负责队列与发布，单插件洞察 Skill 负责证据、详情和观察批次；独立调用洞察不要求生成全轮入口。
共同输出要求只在本文件维护；Skill 保留流程、触发条件和自身特有约束。
字段与引用规则以[数据契约](DATA-CONTRACT.md)及 JSON Schema 为准，
研究判断遵循[研究规范](RESEARCH-STANDARD.md)。

## 研究输出入口

项目根 `README.md` 是面向读者的研究输出统一入口，初始化和更新都须同步维护。
README 必须注明研究起点为以下两个来源并提供直接链接：

- [awesome-dsh-plugin/awesome-dsh-plugin](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin)
- [0xsline/awesome-deepseek-harness](https://github.com/0xsline/awesome-deepseek-harness)

研究结果区按推荐页、分类列表、单插件详细分析提供阅读入口，并保留当前插件档案、最新增量报告及历史报告链接。
注明当前研究范围、截止时间及重要覆盖边界；只链接实际存在的产物，未完成部分明确说明。
没有真实基线时注明尚未初始化，不将合成示例展示为研究成果。

README 是结果导航与摘要，不复制完整档案、证据或报告，也不成为新的研究规则真相源。
更新时保留两个出处链接和历史报告入口，同步最新报告与检查状态；无变化或失败批次仍如实说明边界。
具体版本出处、原始证据和验证条件继续保存在对应档案及报告中。

## 文件位置与命名

| 产物 | 位置 | 要求 |
|---|---|---|
| 研究输出入口 | 根 `README.md` | 维护研究结果、出处和历史产物导航 |
| 当前档案与运行历史 | `data/catalog.json` | 由校验后的计划应用生成，不手动绕过增量逻辑覆盖 |
| 研究清单与进度 | `data/sessions/<session_id>.json` | 固定来源、候选列表及逐项检查点，跨执行恢复 |
| 观察批次 | `data/observations/<run_id>.json` | 保存本次成功观察和失败目标，与档案运行 ID 对应 |
| 原始证据 | `data/snapshots/<run_id>/` | 使用可辨识来源／组件和用途的文件名，保留固定版本与采集时间 |
| 执行结果及日志 | `data/snapshots/<run_id>/` | 标明命令、环境、结果及边界，由执行证据引用 |
| 研究报告 | `data/reports/<run_id>.md` | 按下述共同结构记录本次研究，不重写历史报告 |
| 分类列表 | `data/reports/<run_id>-catalog.md` | 按业务分类汇总四标签短评，链接单插件详情 |
| 推荐页 | `data/reports/<run_id>-recommendations.md` | 从已完成分析中形成采用／试用建议，注明时间、范围及证据层级 |
| 临时计划 | 系统临时目录 | 用于检查候选档案，不默认纳入版本管理 |

`run_id` 在工程内唯一，推荐 `YYYYMMDDTHHMMSSZ-init` 或 `YYYYMMDDTHHMMSSZ-update`，
必要时增加可辨识后缀。ID 只使用字母、数字、连字符和下划线，不能包含路径分隔符或 `..`。
采集时间与截止时间使用带时区的 ISO 8601；文件名中的时间统一用 UTC 并加 `Z`。
数据字段继续使用 Schema 中的稳定名称和枚举，报告正文使用中文。

原始文件不得含凭据。证据 `artifact` 使用工程根目录下的相对路径；可核查的外部来源另外保存 URL
和版本。实际已执行的测试才生成执行证据，不以示例日志或作者提供的日志冒充本地执行。
`examples/observations.json` 仅用于说明与测试，不计入真实目录及统计。

## 研究清单与断点

每轮先确认来源、固定版本与覆盖范围，再用 `research-session.mjs start` 生成 JSON 会话清单。
清单格式、变化标记和状态由[数据契约](DATA-CONTRACT.md#研究会话与脚本检查点)及 Schema 维护，
不另建手工 Markdown 状态表。身份待核实、明确排除和范围差异写入本轮报告，不能静默漏项。
原始证据与部分分析及时落盘；checkpoint 只代表目标插件本轮分析和入档完成，不代表实际安装验收。

首轮与后续轮次都重新分析全部纳入清单的插件，随后生成分类短评与推荐；
只有同轮恢复才跳过 complete 项。对比旧分析，分别说明插件变化与判断变化；
代码未变也要重新核查场景、替代办法、依赖、价格、流程和收益条件。
旧证据可在版本与适用条件匹配时引用，旧结论不直接继承为本轮结论。

汇总报告列出新增、来源移除、路径／内容／来源变化、未变和未知，标记可重叠，不能相加当插件总数。
同时给出总数、完成数、待处理数及受阻项；next 为空但有 blocked 时仍未完成。
阶段结果标明范围，不把部分完成写成全轮完成；会话、观察批次由轮次报告链接；README 仅导航推荐、分类、详情与历史。

## 先分析，再归纳与推荐

研究生成顺序为“单插件详细分析 → 分类列表 → 推荐页”。先完成证据和采用画像，
再提炼短评与推荐，不能先定榜单再寻找支持材料。读者可从 README 的推荐页或分类列表进入详情。

- **单插件详细分析：** 放在本次研究报告的独立小节，提供稳定锚点；覆盖场景与原有办法、
  依赖、使用及失败恢复流程、成本与效果、采用点评、证据和验证边界。规模扩大确需拆分时，
  使用 `data/reports/<run_id>-<component_id>.md`，由本次报告链接，不复制两份当前分析。
- **分类列表：** 以业务场景为主分类，技术类别作为辅助信息。每个插件使用下述四标签短评，
  标题链接到对应详细分析；标明范围、截止时间和研究深度，未深评条目明确哪些内容仍未知。
- **推荐页：** 最后从已完成详情中筛选，链接对应分析。说明推荐给谁、为什么、关键质疑、
  必要依赖与成本、证据层级及最小试用方法；未形成推荐时直接说明原因，不凑数。

推荐页区分两个用途：

- **什么值得装：** 面向持续采用，必须有目标版本的实际安装与真实宿主验收证据，
  并明确用户场景、收益依据、持续负担和兼容范围；证据缺失或过期时保留待验证状态。
- **本周最值得试：** 面向小范围探索，说明本周哪项新发现或变化值得验证、适合谁、
  试什么以及成功／停止判据。源码级证据可支撑试用候选，不能据此写成已验证增效；
  明确本周起止日期与候选覆盖范围，不把有限样本写成全生态最佳，也不隐含定期执行授权。

每轮重新完成全部纳入清单的详情，再生成分类短评和推荐；历史报告作为对照链接并保留原文。
同轮续跑复用已完成项，README 指向实际生成的最新产物。
不为输出格式重新初始化数据或增加 Schema 字段。

## 报告共同结构

报告至少覆盖以下内容；允许根据规模合并小节，但不能遗漏事实边界。

1. **范围与截止时间：** 本次模式、运行 ID、来源、目标插件、采集截止时间及排除范围。
2. **来源覆盖：** 成功与失败来源、固定版本、分页／截断／权限限制，以及是否足以支持总体统计。
3. **结果统计：** 按下述模式说明条目、组件、仓库及变化情况，写清统计口径。
4. **研究结果与变化：** 区分事实、解释与决策影响，按下述洞察结构说明关键判断及证据；记录代码／功能／风险面积，无实质变化时直接说明。
5. **结论状态：** 本次新增、修订、仍有效及待复核结论，包含受影响的同类比较和生态缺口判断。
6. **验证与边界：** 区分作者报告、源码核查、本地测试、真实宿主验收和独立反馈；记录实际结果及未覆盖项。
7. **未完成项：** 采集错误、待核查问题、下一步最有价值的验证及采用条件。

没有相关内容的部分注明“不适用”及原因；验证未执行写“未执行”，不能写成通过或失败。
报告中的数量、版本、结论状态必须与观察批次和应用后档案一致。大规模明细保留在结构化数据中，
报告概括关键变化并引用具体条目及证据，不复制全部原始数据。

## 插件采用画像

重点点评及专题比较先交代业务场景和原有办法，再呈现采用条件、流程、成本与结果。
按[研究规范](RESEARCH-STANDARD.md)的六个维度组织，不能用架构和代码质量清单代替这些内容。
目录级条目未完成核查的维度标明未知或作者声明，不要求为全部条目虚构完整测评。

每个重点插件的报告至少能回答：

- **场景与问题：** 用户、任务频率、输入、合格交付物和原有替代办法，具体改善哪一步。
- **依赖：** 安装依赖与效果依赖分别列出；关键项说明用途、必要／可选、版本／权限／付费条件、失效影响和替代方式。
- **流程：** 简述准备、处理、人工确认／写回、验收及失败恢复；区分用户操作、后台执行和异常处理负担。
- **成本：** 分列首次配置、持续使用及迁移成本，注明现金和人工时间、实际／估算、计价日期及工作负载。
  按合格任务计量时同时给出验收标准、合格数、总尝试数和失败／重试／复核是否计入；没有合格结果不输出有限单位成本。
- **结果与选择：** 相对基线的质量、端到端耗时、可靠性和总负担，适合／不适合的人群及成立条件。

缺少数据时说明缺口和下一步验证；不同模型、任务量、免费额度或人工投入下的成本不能不加说明地直接排名。
证据和分析记录到现有 findings 与报告中，不为画像添加未定义的 Schema 字段。

## 洞察表达与专题比较

每条采用、迁移、技术路线或生态机会判断使用以下结构；可用简短段落或表格，不要求机械拆成六节：

| 内容 | 必须回答的问题 |
|---|---|
| 判断 | 一句话说明发现及其状态：证据支持的判断，还是待验证假设；限定研究问题和样本 |
| 支持证据 | 哪些版本、实现、任务结果或独立反馈支持它，分别证明到哪一步 |
| 反例或其他解释 | 什么观察与判断不符，是否存在采样、环境、成本或替代机制的解释 |
| 适用条件 | 哪些用户、任务、宿主／模型版本及环境下可能成立，哪些范围未覆盖 |
| 决策影响 | 对谁的采用、继续观察、迁移或开发优先级有什么改变，收益与代价是什么 |
| 下一步验证 | 最小可执行实验或补证动作、观察指标、成功判据，以及什么结果会削弱或推翻判断 |

洞察围绕“什么场景下，相比什么办法，依赖什么条件，以怎样的流程与总成本，改善什么结果”展开，
再给出采用、迁移或继续观察建议。正文按“事实 → 解释 → 决策”呈现证据链，不能用功能清单或增长数字代替论证。
缺乏运行验证时明确标记机制推断或待验证，不把未验证效果写成排名或收益结论。
不为满足报告结构强行生成洞察；无新判断时说明检查结果、证据缺口及最有价值的下一步。

专题比较围绕共同问题组织，记录候选及选择理由、基线、版本／环境／预算、成功判据、
已验证和未验证的表现、成本及迁移代价。不能对齐的条件单独列明，避免配置不同的结果直接排名。
专题内容放在本次研究报告中；README 链接实际存在的专题报告，并用有条件的摘要说明主要判断。
不要为未完成专题创建结果链接，也不复制完整论证到 README。

生态机会须分别交代供给覆盖、用户问题证据、替代方案代价、真实解决尝试和最小方案验证。
只有目录数量或未发现竞品时，明确限制为供给观察，不能命名为已确认需求或市场机会。
现有结构化 findings 保存判断性质、文本、证据与依赖；上述论证通过报告表达，不要求增加 Schema 字段。

## 面向读者的采用点评

分类列表中的每个插件采用以下四个固定标签，每项用一句或必要的几句短述，方便扫读。
单插件详情的采用点评也按此结构归纳；不把全部内容挤成一句话，不机械限制字数。

- **用途：** 谁在什么场景下完成什么具体任务。
- **亮点：** 相比原有办法，最值得关注的能力或流程改善；注明作者声称、机制推断或实际验证。
- **关键质疑：** 最影响采用决策的问题及其后果，围绕收益归因、依赖、流程负担、总成本或承诺范围。
  已确认的限制直接陈述，不包装成悬而未决的问题；尚无答案的质疑写清缺口，不能暗示已证实无效。
- **建议：** 适合谁、在什么条件下安装／试用／继续观察／暂缓采用，以及优先验证什么。

短评由详情归纳，必须保留会改变选择的条件；每项突出重点，不重复完整论证。
每轮重新形成点评，说明与历史判断一致或改变的依据；历史报告保留原文。

- 使用具体任务、机制与后果，例如把“流程复杂”改成“首次要维护本地 OCR 环境，偶发收票者可能难以摊薄配置时间”。
- 把“快／便宜／自动化”的主张与合格率、全部预算及人工责任连起来；没有实测时使用条件判断。
- 将采用优先级、技术新意和证据强度分开表达；不得用推荐程度暗示已完成宿主验收。
- 保留会改变选择的证据和边界，避免宣传式总结、人格嘲讽、无依据的失败断言，以及每个插件都能套用的泛泛警句。

采用点评由现有分析归纳，不充当新的证据。它与完整洞察共用证据链，
记录在报告及分类列表中，不增加 Schema 字段；README 只保留有条件的摘要并链接相应产物。

## 每轮统计与历史比较

首轮说明候选、去重组件和仓库数、条目类型、分类分布、研究深度及未核查范围。
后续轮次增加来源与插件变更统计，并逐项对照“旧判断 → 本轮证据 → 当前判断 → 决策影响”。
无变化不免除分析；没有新洞察如实记录，不为制造差异改写观点。失败与受阻不导致删档。
统计应与脚本会话、观察批次及应用后的档案一致，不能把目录供给量写成可用插件数、用户量或需求规模。

## 交付验收

应用计划前检查候选档案和语义变化；基础档案变化时重新生成计划。
交付前必须执行档案校验及工程约定的行为测试，并校验本次观察批次：

```sh
node scripts/plugin-data.mjs validate --observations data/observations/<run_id>.json
npm test
```

同时人工核对 README 结果入口与来源链接是否完整、所链接产物是否存在、证据文件是否存在、
来源版本是否可追溯、报告与数据是否一致、失败是否被正确保留，
以及待复核结论是否仍被误写为当前版本的验证结果。
核对详情、四标签短评与推荐是否一致，推荐是否区分安装与探索试用，周推荐是否写明日期和范围；
不得将源码级候选包装成已验收安装推荐。
洞察还需核对事实与解释是否分开、比较条件是否可比、是否检查反例、决策影响是否有适用条件，
以及下一步验证能否支持或推翻判断。还须检查安装依赖是否被误当效果保证、后台和异常成本是否遗漏、
成本单位是否对应合格任务，以及现金与人工时间是否被无依据混算。数据校验通过不代替这些语义检查。
当前自动校验覆盖结构、身份、引用、会话检查点及增量写入行为；它不自动验证报告叙述、证据内容真实性或实际宿主效果。

将 README 入口更新与本次档案、观察批次、证据及报告作为一个可检查的交付组合。
提交／推送／PR 操作沿用用户授权和根 `AGENTS.md` 的仓库约束；本地校验与远端 CI 结果分别报告。
面向用户的交付说明给出结果入口、关键变化、验证结果及未完成边界，不要求用户从过程消息中拼接结论。
