# 提交规则

## 目的

定义 `dsh-plugin-insight` 的提交授权、范围、消息格式、验证、文档同步和历史修改规则。
沿用 Convivium 的提交治理原则，按当前单工程结构适配。
Commit 记录一个明确工程判断或小步变化，不表示阶段交付完成；PR、Review、CI 和合并由
[PR 规则](PR-RULES.md)维护。

## 授权

- 修改完成后默认保留工作区；只有用户明确要求提交时，才执行暂存和 commit。
- 用户只要求修改、检查或验证时，不自动 commit。
- 暂存、commit、push、创建 PR 和合并 PR 是不同操作，不从单项授权推断其他未表达操作。
- 用户可以一次授权多个操作，已经明确的组合授权持续有效，不逐步重复确认。
- 提交只包含当前任务范围，不纳入无关、归属不明或用户已有的修改。

## 提交边界

- 一个 commit 表达一个可用一句话解释的工程判断、能力变化、测试约束、配置或文档落点。
- 同一判断涉及的代码、测试、Schema、配置和文档放在同一 commit。
- 独立判断、独立风险或可单独回滚的变化分别提交。
- 不为减少数量机械 squash，也不为追求小文件数拆出不可独立理解或验证的状态。
- 文件数量只用于检查内聚性，不作为机械拆分标准；不夹带格式化、重构、个人配置或临时文件。
- 研究交付按[输出标准](../01-design/OUTPUT-STANDARD.md)维护 README、档案、观察批次、证据与报告的一致性。

## 消息格式与工程登记

```text
Type(<project>[/<module>]): <中文工程判断>
```

Type 使用 Feat、Fix、Docs、Test、Refactor、CI 等准确类型。
project 必须从下表选择；module 可选，用于稳定模块或治理域，不代替工程标识。
中文说明表达形成的判断或能力结果，避免只有“调整”“修改”“优化”的描述。

| project | 对应范围 | 使用边界 |
|---|---|---|
| `repo` | 当前根 package 对应的单工程：研究数据、Skill、脚本、测试、治理与 CI | 不虚构尚不存在的独立插件或服务工程 |

示例：

```text
Docs(repo/governance): 分离提交与 PR 交付规则
Feat(repo/data): 保留失败采集前的插件档案
CI(repo): 校验研究数据与增量行为
```

新增独立构建、测试或交付的工程时，在同次初始化中登记唯一工程名并更新相关配置。
业务域放在 module 或说明中，不用临时简称替代 project。
当前没有多工程交付，不预设 cross-project；确需不可拆分的跨工程判断时先补充登记及范围规则。

## 提交前验证与同步

1. 检查工作区和完整待提交差异，确认授权、范围、无凭据及无关个人文件。
2. 按根 `AGENTS.md` 执行相关检查；已有且仍适用的验证证据可复用，不因提交动作机械重跑。
3. 按[文档规则](DOCUMENT-RULES.md)检查需求、契约、实现、输出及路由同步，只同步实际受影响部分。
4. 消息如实表达本次完成点及验证边界，不将未完成范围写成完成。

只有实际涉及已登记任务或临时执行文档时才收口对应内容，不为了提交新增任务或证据模板。

## 历史安全

- 不自动 amend、rebase、squash 或改写已有 commit；只有明确授权才能修改历史。
- 已推送或进入协作范围的历史，须有针对具体范围与风险的明确授权后才可重写。
- 允许更新远端历史时使用 lease 保护，不使用无保护 force push，也不绕过 main 保护。
- 不以破坏性操作丢弃用户提交、工作区改动或未跟踪文件。
