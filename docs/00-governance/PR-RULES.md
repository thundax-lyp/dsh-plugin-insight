# PR 规则

## 目的与真相源

定义本工程的分支、PR、Review、CI 与合并边界。提交授权、粒度与格式由
[提交规则](COMMIT-RULES.md)维护。
CI 执行内容以[工作流](../../.github/workflows/ci.yml)为准，命令与依赖由根
[package.json](../../package.json)、锁文件及 `.node-version` 维护。
远端实际强制检查由 GitHub 分支保护或 Ruleset 决定；本文不保存其配置快照或核验历史。

## 交付与分支

- 开发变更通过分支、PR、Review、合并进入 main，不直接推送开发中的改动到 main。
- 分支使用 `codex/` 前缀及简短稳定的英文语义，围绕同一阶段目标，不混入无关工作。
- 一个 PR 围绕可说明、可验收的目标组织，可含多个符合提交规则的 commit。
- Draft PR 仍说明范围、风险和未完成项，不以 Draft 状态省略交付边界。
- GitHub 操作复用当前环境可用的 GitHub Skill 或插件；本规则定义约束，不复制工具调用流程。

## main 与合并方式

项目期望 main 变更必须经过 PR，禁止删除和强制推送，合并前解决评审讨论，
并基于最新目标分支通过全部必需检查。
采用普通 merge commit 保留分支提交及完整历史，不使用 squash merge。

合并前实时核对分支保护／Ruleset、必需检查、审批要求、允许合并方式及 PR 最新状态。
缺失检查不等于通过，本地绿色不代替远端门禁；发现策略差异如实报告，不绕过保护。
修改远端规则须有对应授权并回读确认，新增本文不会自动修改 GitHub 配置。
只有用户明确授权才能合并，组合授权按 COMMIT-RULES 解释。

## 标题与描述

标题使用 `Type(<project>[/<module>]): <中文阶段交付结论>`，project 来自提交规则的登记表。
描述使用[PR 模板](../../.github/pull_request_template.md)，说明问题、最终行为、范围、验证和未覆盖项。
简单变更可在适用栏目各写一句，不重复罗列文件或描述过程历史。

验证写实际命令、结果和边界，未执行项不写通过，不适用项注明原因。
不包含凭据、个人绝对路径、机器信息或 Agent 内部过程。
范围调整后同步标题与描述，反映最终实现及最新验证。
研究交付需提供 README 结果入口及本次覆盖范围，遵循[输出标准](../01-design/OUTPUT-STANDARD.md)。

## 验证与评审

- 复用仍适用的本地证据；新变化影响已有结果时补充相关验证，不做无依据的重复测试。
- 合并必须满足远端全部必需检查，具体执行以 CI 工作流为准，不在模板或规则复制检查清单。
- 评审基于 merge base 检查完整 PR 差异，结合正式依据、失败路径和证据判断。
- 可执行 finding 说明触发条件、可观察影响及修正方向；区分问题成立与建议方案是否合适。
- 处理明确反馈后验证受影响行为，不报告纯风格偏好或无依据的猜测。
- 结构校验与行为测试不证明研究结论真实，也不证明真实 DSH 插件可用。
- 数据、证据、报告、README 和治理同步按文档规则及输出标准核对，不为不适用项创建新材料。

## GitHub 调用通道与授权

GitHub Skill／插件与本机 gh 的凭据和权限可能不同。
插件不支持操作或返回权限错误时，可使用已认证且有对应权限的 gh 完成同一已授权目标；
切换通道不扩大授权，也不绕过访问限制或仓库保护。
调用前确认目标仓库、PR 或讨论标识；使用 gh 时确认其认证和目标仓库访问权限。
写操作后回读目标状态，命令成功返回不等于最终状态已确认。

创建 PR、回复或解决讨论、推送、关闭及合并等写操作，均须对应当前用户授权。
记录必要的权限失败与未完成边界，不把它们误写成通过。

## CI 演进

工作流清楚显示必过检查及实际覆盖，不以聚合脚本替代可审阅的 CI 结果。
修改 job 名称或远端保护时核对二者一致，防止缺失检查阻塞或无检查放行；
远端配置修改仍须单独获得对应授权。
治理或工作流变化执行相称验证，结果写入 PR 或实际交付证据，不将运行快照复制回治理规则。
