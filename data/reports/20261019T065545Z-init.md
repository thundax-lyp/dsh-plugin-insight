## InvoiceFlowAI：从邮箱到报销准备材料

### 场景、问题与基线

**目标场景：**个人、自由职业者或小团队定期从 QQ／163 邮箱收集电子发票，人工下载附件或链接、识别票面、按类别归档，再填 Excel 清单。合格任务应是“可追溯的票据原件＋关键字段正确的汇总＋明确的待复核项”，不等于已经通过单位报销、税务或会计审核。

**作者主张：**插件在 DSH 侧栏串起 IMAP、识别、归档、Excel 汇总。源码可见模型提取和本地安装链路；本轮未验证真实邮箱扫描、原件完整性、去重、字段准确率和汇总一致性。

**比较基线：**人工邮箱下载＋Excel；同仓库独立桌面应用；用户已有的报销系统。已有桌面版用户能否从 DSH 集成获益，应看是否需要复用现有宿主模型与工作区，而非假设“装插件必然更省事”。这些基线本轮均未进行同条件实测。

### 依赖与成立条件

| 依赖 | 必要性及作用 | 使用负担／失效影响 |
|---|---|---|
| DSH Web、Node 与宿主服务 | 安装必需；包声明 Node `^22.19.0 || >=24`，依赖凭据、LLM、会话和子进程服务 | peer 范围不是当前宿主验收矩阵；本次没有真实宿主兼容结果 |
| Windows x64 或 macOS Apple Silicon、本机 Python 3.10+ | 作者明确支持的插件平台与本地引擎前置 | 不把桌面独立应用的“无须安装 Python”迁移成插件版能力 |
| pip、RapidOCR、Chromium | 安装器创建虚拟环境，下载 Python 依赖，并执行 Playwright Chromium 安装 | 首次联网、磁盘、安装和后续维护成本；安装失败尚未实测 |
| QQ／163 IMAP 及授权码 | 收票必需；需要邮箱访问许可和正确时间范围 | 登录、邮件可见范围和票据来源决定候选完整性，不能只看识别率 |
| 当前 DSH 模型和可用额度 | 默认 OCR 文本结构化提取的效果依赖 | 源码通过当前模型选择发起调用；模型质量、输出格式、预算影响成功和复核量 |
| GLM 凭据与图像服务 | 可选降级分支，需配置才启用 | 额外服务依赖和可能的图像外发；不是默认零成本本地识别 |
| 人工核验与可用票据数据 | 结果使用必需 | 清晰度、字段标准化、下载链接有效性、公司抬头和凭证配对决定可交付比例 |

证据：[插件说明](https://github.com/EthanYoQ/Invoice-Downloader/blob/8fe3a1147c619268b41f1480e73c4fa38d97db69/plugins/dsh-invoice-downloader/README.md)、[包清单](https://github.com/EthanYoQ/Invoice-Downloader/blob/8fe3a1147c619268b41f1480e73c4fa38d97db69/plugins/dsh-invoice-downloader/package.json)、[安装器](https://github.com/EthanYoQ/Invoice-Downloader/blob/8fe3a1147c619268b41f1480e73c4fa38d97db69/plugins/dsh-invoice-downloader/runtime/install.py)。

### 流程复杂度

- **用户可见：**安装插件 → 安装本地引擎 → 配置邮箱授权、模型和保存目录 → 设定时间／公司范围 → 扫描 → 核验票据及汇总 → 提交到原有报销流程。
- **后台实际：**IMAP 收集 → 附件／链接恢复 → 确定性解析或本地 OCR → 宿主模型提取 → 必要时可选 GLM 降级 → 归档和报表。识别链及引擎桥可见，完整端到端顺序与分支效果尚未运行验证。
- **失败处理：**安装、认证、模型调用、下载链接和识别均可能形成不同处理负担；模型桥存在错误返回，产品保留人工复核路径。不能假设每种失败都能无损自动恢复。

**解释：**插件把重复收集与整理搬到一个批处理入口，但没有消除数据接入、依赖部署和最终复核。票据量越少、数据越不规则，前置配置和人工善后越可能抵消收益。

### 洞察与采用决策

**判断：**更适合作为已有 DSH 用户的“报销准备批处理助手”，而非“免配置、全本地、自动完成报销”的系统。

**支持证据：**插件专用 README 与安装器要求 Python、pip 和 Chromium；`invoice-scanner.ts` 将提取请求交给当前宿主模型；`dsh_runner.py` 根据 GLM 凭据决定是否建立可选降级链。[模型桥源码](https://github.com/EthanYoQ/Invoice-Downloader/blob/8fe3a1147c619268b41f1480e73c4fa38d97db69/plugins/dsh-invoice-downloader/src/invoice-scanner.ts)

**其他解释／反例：**首次配置可由技术人员完成，已有 DSH 用户的边际成本可能较低；如果确定性解析覆盖多数票据，模型成本也可能较小。反过来，直接桌面版或现有报销平台可能更省准备工作。本轮没有数据判断谁更省。

**适用条件与影响：**票据集中在支持邮箱、可接受由配置的模型服务处理票据内容、愿意核验且有重复整理工作时，值得小规模试用。偶发少量票据、仅移动端、禁止文本／图像外发或需要正式审批闭环时，须先验证符合条件的替代链路，不能直接沿用默认流程。

**最小验证（尚未执行）：**取同一批已人工核对的混合票据，覆盖附件、下载链接、模糊材料和重复件。分别跑人工基线与插件；记录候选完整性、关键字段全对的合格数、原件／报表对应关系、复核分钟、总耗时、现金账单和失败尝试。若人工总时间不下降，或关键字段／原件不满足验收标准，则削弱采用建议。价格日期和模型路由随测试记录。

## TaskSwarm：把可拆分开发任务排成并行批次

### 场景、问题与基线

**目标场景：**代码仓库中有多个边界清楚、验收明确且依赖可描述的任务，需要并行推进再集成。原流程是开发者或主 Agent 手动分任务、建分支／worktree、切换上下文、评审和合并。

**合格交付物：**满足任务标准、通过约定集成验证、可追溯且没有重复或越界变更的集成结果。worker 自报完成或分支合并成功都不等于合格批次。

**作者主张：**任务包、依赖波次、worktree lane、Reviewer、Merger 和磁盘检查点形成项目级编排。作者关于 DSH 原生能力的对比属于该 README 的描述，不能自动作为 2026-10-19 当前宿主能力的事实。本轮未测试当前 DSH 原生基线。

### 依赖与成立条件

| 依赖 | 必要性及作用 | 使用负担／失效影响 |
|---|---|---|
| DSH、Node ≥22、Git、可写仓库及 worktree | 安装和运行基础；包暴露 `dsh.bundle` | peer 为通配范围不证明当前宿主兼容；源码安装有 `prepare` 构建步骤 |
| 任务包、依赖关系、验收标准 | 效果必需；每任务需定义 PROMPT／STATUS 等材料 | 需求耦合或验收模糊时，拆分、同步和返工可能超过并行收益 |
| Worker 模型及额度 | 每个 lane 运行 Agent | 同时运行需要模型容量、项目环境及本地 CPU／内存／磁盘；实际并发上限未测 |
| Reviewer／Merger 模型能力 | 按配置执行评审，冲突时可能再启合并 Agent | 独立会话不保证更强模型；评审和语义合并均增加调用及验证成本 |
| 开发者验收和故障处置 | 效果必需 | 仍需处理冲突、残留状态、失败 lane 和最终集成正确性 |
| 可用分发入口 | 采用前置 | 2026-10-19 公共 npm latest 直接查询为 HTTP 404；GitHub 源码可读，但 GitHub 安装本轮未执行 |

证据：[源码清单](https://github.com/february2015/dsh-taskswarm/blob/032e2c9d228c20cab65fe0ea061d78a7c753ab8c/package.json)、[npm 查询证据](../snapshots/20261019T065545Z-init/taskswarm-npm.json)、[操作手册](https://github.com/february2015/dsh-taskswarm/blob/032e2c9d228c20cab65fe0ea061d78a7c753ab8c/docs/runbook.md)。不能把仍保留的“8 月 19 日恢复 npm”文字当成当前安装事实。

### 流程复杂度

- **用户可见：**核对安装／宿主 → 为任务写输入、限制和验收 → 预览依赖波次 → 启动批次 → 监控异常 → 核验集成分支 → 将结果并入目标工作分支。
- **后台实际：**按波次调度独立 lane → Agent 工作与检查点 → 按任务要求评审 → 串行合并 → 冲突时可调用 Merger → 下一波。worktree 隔离文件写入不等于外部服务、数据库、端口或测试资源隔离。
- **失败处理：**手册说明崩溃后磁盘状态保留，但内存活动表清空，普通 pause/resume 可能提示无运行批次；需核对现状、保留分支并重跑／挽救。不能把“有检查点”理解成任意崩溃点完全自动续跑。该行为未在真实宿主中复现。

**解释：**它减少的是手工调度和可独立任务的等待，把一部分工作转换成任务包管理、模型评审、环境维护和集成验证。单个小修复或多任务同时修改同一核心模块时，额外流程可能不划算。

### 成本画像

- **首次成本：**核对源码安装与宿主服务、准备 Git 工作区、设计任务拆分和可执行验收、验证每个 lane 的依赖环境。
- **持续现金与资源：**Worker 调用之和＋实际发生的 Reviewer／Merger／返工调用，加本地多工作区和构建测试资源。串行集成仍是耗时组成。
- **人工成本：**写任务、审查误判、冲突处置、失败挽救、端到端验收；迁移还需保留任务和分支历史并清理工作区。
- **单位：**一个满足整体验收的开发批次，或一个明确合格的任务；失败、重复和返工费用不能丢弃。本轮未运行批次，无实际耗时、账单、合格率或收益倍数。

在任务独立、资源充足的假设下，一波的工作等待可能从串行求和接近最慢 lane 的耗时，但还要加调度、评审和串行集成。模型总费用仍需按所有调用求和，因此“更快”不自动等于“更便宜”。这只是分析模型，不是实测加速比。

### 洞察与采用决策

**判断：**应按“付费缩短可并行任务的交付等待”评估它，而不是按 Agent 数量评估生产力。

**支持证据：**调度源码中 lane 完成后的合并使用串行队列，冲突才进入可选 Merger；Reviewer 有独立模型请求。任务包和 Git 状态是明确的准备与恢复负担。

**关键限制：**`reviewer.ts` 将不含 `REVISE` 的文本判为 PASS，包括未出现明确 PASS 的文本；`engine.ts` 的评审读取可返回 `none`，非失败、任务状态允许且未判 REVISE 时仍进入合并路径。这不等于每种任务都必须审查，但不足以证明严格“明确通过才合并”。不能用省掉人工评审来计算成本收益。[Reviewer](https://github.com/february2015/dsh-taskswarm/blob/032e2c9d228c20cab65fe0ea061d78a7c753ab8c/src/worker/reviewer.ts)、[调度与合并](https://github.com/february2015/dsh-taskswarm/blob/032e2c9d228c20cab65fe0ea061d78a7c753ab8c/src/orchestrator/engine.ts)

**其他解释／反例：**成熟团队若已有清楚的任务模板、便宜且可靠的模型、可复用测试环境，这些准备成本可能被摊薄；若需求相互耦合或整合测试很慢，并行很可能只增加返工。本轮没有对照实验判断净收益。

**适用条件与影响：**有多个边界清楚的开发任务、熟悉 Git、能维护测试环境并保留最终人工验收的团队，可以先做隔离验证。当前 npm 分发与宿主兼容未过关前不建议直接接入关键仓库；源码可用不等于现成生产工具已就绪。

**最小验证（尚未执行）：**选择同一组可拆任务和集成标准，对比单 Agent 串行与小规模 TaskSwarm。固定宿主、模型、任务和环境，记录拆分／配置时间、端到端耗时、全部模型费用、人工干预、返工与合格批次数。额外注入评审空响应、冲突和中断，确认不会把不合格结果当完成。若时间收益被准备和集成抵消，或误合并需要大量返工，则暂缓采用。

## 本轮形成的判断与未完成项

这是首次基线，没有旧结论可撤回。已形成两条采用层面的解释：发票插件的价值需扣除本地引擎与复核负担；并行开发的时间收益需与模型、环境和集成成本分别计量。它们仍是带条件的采用判断，不是效果证明。
