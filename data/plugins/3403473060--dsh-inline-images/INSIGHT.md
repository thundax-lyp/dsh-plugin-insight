## 当前插件分析

<a id="detail-section-2"></a>

### 使用判断

源码支持下述已实现机制；效果为机制推断，未来假设未验证。

[重点创新推演与最小验证](#innovation)

- **用途**：本机 DSH Web 用户查看截图或生成图，原先需复制路径开文件，现在希望直接在消息中检查并放大。

采用建议：限同机 Web 环境小范围试用，先检查图片展示、重启后历史链接和文件服务权限；敏感图片或远程访问需先明确可读范围。

参照复制路径到系统查看器或手工附件上传；本项目直接展示便利，不能替代附件授权和长期存储。

<a id="detail-section-3"></a>

### 能力、流程与成本

- **后台**：流结束路径改写及回环文件路由
- **界面**：消息正文图片、点击灯箱与尺寸设置

**流程与依赖**

需要 llm、webServer、fs 以及匹配 Typert/slots 的 Web 客户端；尺寸持久化依赖credentials；文件必须仍存在并可由宿主文件服务读取。

模型输出路径→block-end核查文件→写入回环URL→浏览器请求文件→灯箱放大；缺文件跳过，读取异常返回404，尺寸设置独立持久化。

**效果与成本**

首次构建、安装并适配宿主 API；持续有本地文件存储和消息历史链接维护成本，无源码要求的外部图像服务费用；远程拓扑排查需要人工。

减少复制路径和切换应用的步骤有机制依据；图片加载可靠性和端到端省时未实测。

- **思考**：回环链接是否在所有使用环境中可靠？代码固定 http://127.0.0.1:port，因此远程浏览器会访问浏览器自己的机器；重启激活 token 变化也会使历史链接失效。对同机短时查看可成立，不能据此承诺远程和持久分享；扩展名判定也不等于图片内容核验。

### 工程贡献

- **亮点**：相对手动打开本地路径，贡献是把路径识别、文件读取和正文展示串成低操作成本流程；复用宿主文件服务与 Markdown 渲染，属于界面集成而非图像理解机制。反向区间替换避免前一次修改扰乱后续位置。
