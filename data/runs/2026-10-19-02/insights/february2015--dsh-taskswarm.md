# TaskSwarm：先证明交付更划算，再增加并行 Agent

核查对象：`february2015/dsh-taskswarm`，提交 `032e2c9d228c20cab65fe0ea061d78a7c753ab8c`，源码版本 0.2.38。

## 采用短评

- **用途：**把能拆开的开发任务按依赖分波，在 Git worktree 中并行执行，再评审和集成。
- **亮点：**把任务包、隔离工作区、调度和串行合并组织成可观察流程，适合已有测试标准的独立任务。
- **关键质疑：**多 Agent 省下的等待，能否覆盖拆任务、模型评审、冲突处理与最终验收？当前 npm 入口不可用，评审分支也未保证“明确 PASS 才放行”。
- **建议：**目前继续观察；分发与宿主兼容确认后，在可丢弃仓库里试，保留最终人工验收。

## 场景、基线与验收

适合多个边界清楚、依赖关系可表达的开发任务。基线是同模型单 Agent 串行，或人工管理多个 worktree。交付必须在集成后通过共同测试与需求验收，完成了多少 lane 不能代替交付质量。紧耦合重构、规格含糊任务和缺少环境预算的团队可能难以受益。

## 依赖与流程

| 依赖 | 要求和成本 |
|---|---|
| 可用分发与当前宿主兼容 | 源码可读；公共 npm latest 本轮 404，未验证 GitHub 安装；可选 peer 声明不证明当前宿主通过 |
| Git、worktree 和执行环境 | 多份工作区要能独立准备测试、配置与依赖；共享外部资源是否冲突需要另验 |
| 任务定义与验收 | 人要拆边界、DAG、任务包和成功标准；规格不清会把并行变成并行返工 |
| 模型、配额及评审预算 | worker、reviewer、可能的 merger 都有成本；独立会话不等于不同模型或更可靠评审 |

用户定义任务和依赖 → 后台分波分 lane → worker 执行 → reviewer 给结论 → 集成分支串行合并 → 运行整体验收。冲突和失败可能暂停，需要操作员决定修复、重跑或丢弃。

[评审源码](https://github.com/february2015/dsh-taskswarm/blob/032e2c9d228c20cab65fe0ea061d78a7c753ab8c/src/worker/reviewer.ts)将不含 REVISE 的文本判为 PASS；[调度合并逻辑](https://github.com/february2015/dsh-taskswarm/blob/032e2c9d228c20cab65fe0ea061d78a7c753ab8c/src/orchestrator/engine.ts)还存在 none 分支。因此严格的“必须显式通过”不能由评审功能名称推出。这是所读分支的设计限制，不等于每个任务强制评审或所有路径都不可用。

[操作手册](https://github.com/february2015/dsh-taskswarm/blob/032e2c9d228c20cab65fe0ea061d78a7c753ab8c/docs/runbook.md)说明进程崩溃后 active 内存表清空，控制命令可能找不到运行批次；磁盘状态可供人工检查和抢救，但不能把检查点等同于自动无损续跑。

## 成本、收益归因与验证

首次付出拆分标准、宿主适配、工作区和测试环境；每批计入所有 worker／reviewer／merger 调用、失败重试、准备和集成人工时间；还要计入磁盘／计算与迁移维护。

**判断：**并行最直接改变等待时间，是否改善合格交付成本仍无证据。若任务确实独立、串行等待长且集成容易，可能获益；若同一文件反复冲突或评审放行过宽，速度收益可能被返工抵消。更大模型或更高总调用量也可能解释结果，需控制。

先确认分发版本与宿主，然后在临时仓库固定任务、模型和质量标准，对照单 Agent 串行与两 lane；记录拆分时间、合并后合格率、墙钟时间、全部模型账单和人工干预。注入空评审、冲突和中断，检查错误是否被合格验收挡住；若出现未验收误合并或收益不覆盖集成负担，则停止扩大。
