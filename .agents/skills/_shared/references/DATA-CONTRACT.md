## 唯一当前快照与本轮增量

- 当前快照是唯一正式研究真相：当前插件档案、来源状态，以及它引用的当前分析、必要证据和持久受阻状态。唯一性指逻辑上只有一套权威现状，不要求所有材料塞进一个 JSON；生成页面和本轮工作副本不构成第二真相。
- 新一轮只读当前快照作为比较基线，记录摘要；不要求历史会话、历史 manifest 或 runs 归档。当前来源成员清单或比较维度缺失时记 unknown，不能凭研究子集推断全目录移除。
- 本轮先独立生成观察、分析、证据和进度，再合成候选快照。逐项完成只更新本轮暂存区；正式快照在最终合并前保持可用。
- 合并必须校验基线摘要、身份、来源与代码版本、证据引用、结论依赖及生成一致性。基线变化须重新计划；重复应用同一增量不得重复追加事实。
- 合并以一致的事务提交当前档案、分析／证据引用和展示输入；多文件准备阶段不能对外暴露部分新状态，失败仍使用旧快照。实现必须有可回读的提交点及中断恢复办法。
- 未选、失败或未完成项不替换有效的当前记录，不因本轮 pending／blocked 删除旧成果；新证据证明旧结论失效时，可将经过校验的失效记录合并为待复核状态，不伪造完成态。
- 当前结论保留来源 URL、固定版本、证据类型、限制及必要材料。历史 artifacts 键中可能包含 runs 字样，它仅是嵌入材料的稳定标签，读取时不解析为本机文件路径。合并时将仍需引用的材料落入正式快照位置，不让有效结论依赖可清理的 runs 路径。
- 合并回读成功且当前快照可独立校验、生成页面后，本轮不再被引用的材料可清理；未合并增量保留用于恢复。历史变迁由 Git 追踪，不要求每轮永久归档；本规则不自动授权删除既有文件。

正式快照采用 v4 组件目录存储，由 [组件存储 Schema](../schemas/component-storage.schema.json) 约束。组件目录与 `data/plugins/<plugin-slug>/` 使用同一已登记的稳定 slug，仓库改名或组件移动不自动重命名；稳定身份仍为 `github:<仓库数字ID>:<组件ID>`，索引内部 ID 继续由该身份计算 MD5，不使用 slug 代替身份。

- `data/catalog/<plugin-slug>/research.json` 是该组件唯一的当前研究成果，保存身份、固定研究版本、完整研究档案、分析原稿、结论／评分／采用建议、展示输入与全部必要证据正文。`artifacts` 按原引用标签嵌入证据，不要求旧材料统一格式；原内容及哈希逐字保留。不同组件即使使用相同材料也各自保存，不通过另一组件或共享 evidence 目录读取。已知历史缺失材料在 `unavailable_artifacts` 中明确保留，不补造原件。历史组件若缺少研究原稿、只剩既有发布稿，可在同文件的 `retained_documents` 保存该稿原始字节及哈希作为迁移保留稿；不据此生成有效发布记录或推荐，重新研究成功后清除保留稿。
- 同目录 `meta.json` 仅保存 GitHub／npm 等 META。可独立刷新，不修改 research.json、研究版本、结论或研究时间。保留研究但没有历史 META 的组件以 null 明确表示缺失，不补造指标。
- `data/catalog/index.jsonl` 是查询索引，按稳定身份 MD5 排序，保存 slug、查询字段及 research／meta 各自的字节 SHA-256，不保存独有研究事实。`snapshot reindex` 可从组件目录重建索引，仍需全局 state 完成顺序和整体一致性校验。
- `data/catalog/state.json` 保存全局来源、逻辑顺序、事务、摘要及独立持久受阻状态。受阻是操作状态，不覆盖已有成果；没有成功研究的受阻项不创建正式组件研究目录。扫描候选、最新发现指纹、逐题计划和暂存材料仅在本轮 runs，不写入任何未研究组件的当前成果。

共享 `snapshot-storage.mjs` 校验身份、slug、路径、符号链接、格式、摘要和证据自包含性，还原 [snapshot Schema](../schemas/snapshot.schema.json) 的兼容逻辑对象。逻辑 `discovery.plugins` 仅从最后完成且有发布记录的研究基线派生，不保存全目录扫描状态，`complete_baseline` 为 false；不能据研究子集推断完整目录移除。下一轮重新扫描来源，与 catalog 中最后完成研究的版本比较，不读取上一轮 runs。扫描全目录不等于更新全目录成果，额度外对象保持原研究文件；目录维护信息不再独立写入研究成果，META 按显式刷新流程更新。

迁移使用 `snapshot migrate-storage --backup <新的备份目录>`，将 v3 组件分桶与共享证据显式迁为 v4。先保存全部旧物理字节（包括未提交修改），再持锁事务写入并回读校验。逐项研究档案、原稿、证据内容、META、评分和建议保持不变，仅调整存储与 META 引用位置，扫描候选退出正式档案；旧 v3 仅读取兼容，不能继续写入。历史 v1／v2 读取器仍用于旧材料，不能把迁移视作新研究。没有旧 runs 时迁移、校验及文档重建均可独立执行。

本轮完整逻辑状态由 [工作文件 Schema](../schemas/snapshot-work.schema.json) 约束，拆分入口、队列、状态和兼容链接由 [存储 Schema](../schemas/work-storage.schema.json) 约束。新建过程使用 v2 拆分存储：WORK 只保存 base_digest、INPUT／QUEUE／会话状态／单项记录的路径和 SHA-256；INPUT 保存唯一完整候选清单，QUEUE 保存按输入下标分组的变化及缺席项，状态文件只保存会话头与非默认状态／检查点，已完成记录逐项独立保存。SESSION.json 是指向同目录 WORK 的兼容入口，不另存完整清单。
读取器校验引用路径、内容摘要、Schema、队列覆盖、选择和检查点后，重建原 v1 内存结构；内存结构的语义摘要保持不变，不因拆文件改变已有合并计划、事务标识或结论。session.base_digest 仍绑定正式快照，previous_digest 仅兼容旧工具。
已暂存的 WORK 单项记录包含本项全部证据正文，检查点校验优先读取该内嵌材料并核对内容 SHA-256，不要求 artifact 标签对应的历史 runs 文件仍存在。复用当前成果的同版本材料时，从正式快照复制其正文进入本轮 WORK；若同名物理材料仍在且内容不同，拒绝复用该不可变标签。当前轮的观察批次与原稿仍须存在并匹配检查点；未暂存的新材料仍须从本轮实际文件取得，不以“允许复用”替代新研究。

过程依赖对象按内容摘要命名且不可变，更新先准备依赖、再原子替换唯一 WORK 索引；中断前后读取旧／新完整状态。SESSION 入口通过 WORK 读取当前会话，不独立切换状态；未引用的中断残留不当作完成记录。引用只能落在本轮目录，拒绝路径逃逸、符号链接逃逸与摘要不符，不自动修正损坏内容。
旧 v1 可继续读取；显式 `snapshot migrate-work --work ...` 只预览，加 `--apply` 才迁移。先保留 WORK／SESSION 原始字节到本轮 migration-originals，再生成、回读并核对完整语义摘要后切换 WORK；重复执行不得覆写备份或重置选择／状态。迁移不依赖当前正式基线仍匹配，也不执行研究或修改 SNAPSHOT。正常暂存旧 v1 保持旧格式，避免隐式迁移。
合并计划从固定基线和经过校验的 WORK 重建结果；持有 `index.jsonl.lock` 后复核基线、WORK 与结果摘要。写入器先构建并回读完整候选，再在 `.transaction/` 保存所有变更及删除文件的旧字节与撤销清单，逐文件原子替换，最后更新 state 与 index。事务存在期间读取拒绝返回部分状态；普通失败自动回滚，中断后确认无活动写入者并处理遗留锁，再用 `snapshot recover-storage` 回滚。重复 apply 不追加事实，无变化不重写组件文件。旧分桶及共享证据在迁移事务内删除，原始备份在 catalog 外保存，未知文件不清理。

页面从 catalog 当前研究及 META 重建，生成中断可重跑。生成不读取 runs、manifest、checkout、网络或插件代码，不刷新研究时间。发布稿不是第二份人工真相源。

## 身份与分类

- `identity = github:<repository_id>:<component_id>`，物理 `id = md5(identity)`；仓库数字 ID 与已分配组件 ID 是身份，名称和路径不是。
  改名、路径移动保留身份，旧位置进入 `aliases`；相同 URL 下重建而数字 ID 不同的仓库是另一身份。
- 同仓库不同组件可分别建档；`entry_type` 表示条目类型，技术主类与业务主类各一个，`tags` 可多个。
  分类含义由[研究规范](../../dsh-plugin-insight/references/RESEARCH-STANDARD.md)定义，目录收录不证明可安装。

## 指纹、来源与证据

- `fingerprints` 保存各方面最后一次成功核查的内容版本：`directory` 为目录条目，`code` 为代码，
  `release` 为发布版本及产物，`compatibility` 为支持声明及已验证环境，`maintenance` 为维护状态。
  指纹是固定提交、文件树／文件 SHA 或确定性内容哈希，不能用采集时间代替；未检查的方面省略并保留旧值。
  默认分支与发布包的指纹不可互相冒充。
- `sources` 绑定 URL、`revision` 与 `retrieved_at`；`membership` 表示该来源的 present／removed／unknown。
  来源按 URL 比较最新成功快照，一个来源缺席不代表所有来源均已移除。
  当前研究基线中缺席的组件，只有已知相关来源完整核查时才可判为目录移除，否则标 unknown 并保留原成果。尚未研究的候选仅在本轮 INPUT／WORK 保留，后续轮次重新扫描，不从旧 runs 恢复目录成员全集。源码位置、目录成员及指纹均与最后完成的研究比较，不以未研究的新发现替换基线。
- 同一来源／证据 ID 不得复用为不同内容，内容变化使用新 ID。证据 ID 全局唯一，来源 ID 在插件内唯一。
  当前快照保留支撑有效结论的对象；无当前引用的历史材料不要求永久累积，清理须检查引用完整性。本轮候选复用合并器的身份、来源与依赖校验，正式快照不累计 runs 日志。
  完整复核成功的组件以本轮来源和证据替代过期集合；仍被其他当前结论引用的证据保留。嵌入原件与缺失原件清单同步按当前引用收敛，不随每轮永久增长。
- 证据 `kind` 区分作者声明、源码核查、本地测试、真实宿主验收与独立反馈，均绑定版本并记录边界。
  `artifact` 引用材料；执行证据还必须有 `environment` 与执行结果文件，材料不得保存凭据。
- `research_depth` 的 catalog／source／tested／host_verified 表示已有证据层级；提高层级须有对应证据。
  历史执行证据不自动证明当前版本通过，源码与作者声明不等于运行效果。

## Git 原始材料的可追溯定位

Git 文件采用 evidence.git_refs 保存结构化定位，以[Git 引用 Schema](../schemas/git-reference.schema.json)为准。每项必含原始 `repository_url`、完整 `commit`（40位SHA-1或64位Git SHA-256）及仓库内相对 `path`；分支、标签、短SHA或采集时间不能替代提交。可附成对的 `line_start`／`line_end`、符号名 `symbol` 和文件内容的 `content_sha256`。路径须规范化，不含绝对路径、反斜线、空段、`.`或`..`；URL不能含凭据、查询参数或片段。关键判断仍由 summary、finding 或逐题 observation 说明，定位不能代替论证。

此定位足以表示文件可追溯，不要求将整个上游仓库复制进本仓库。固定版本URL是方便点击的展示形式，不能代替三个定位字段；摘录或已保存快照是补充保全材料。可追溯不等于永久可取得，上游删除、转私有或提交不可达时须说明访问缺口，不能默认为新核查成功。需要重新获取时核对提交、路径与已有内容摘要。

这条规则仅适用于Git中的原文件。npm/API返回、网页、Issue页面快照、运行日志、测试与宿主验收结果须另存当时材料和采集／执行条件，不能用源码提交证明当时服务状态或执行结果。既有artifact及缺失原件清单保持原状态，不因存在源码定位就宣称非Git原件已恢复。

新研究按此格式记录；旧记录暂兼容既有固定版本URL，不强行回填未知的仓库、提交或路径，不复用原证据ID伪装成新核查。执行证据仍须有artifact和environment。

## 结论与依赖

- `findings` 保存主题、结论、判断性质、`evidence_ids`、`dependencies`、`reviewed_at` 与状态。
  依赖绑定稳定插件 ID、核查方面及当时指纹，跨插件比较必须记录相关对象的依赖。
- 生态供给结论也依赖来源总体指纹，可将目录作为 `resource` 条目并依赖其 `directory` 指纹；
  目录变化不冒充单个插件代码变化。
- 贡献、关键质疑和新创新假设的论证复用现有 `findings` 主题与判断性质，完整推导写入报告；两轴创新评分使用下述 `innovation_scores`，不将新假设转成插件已有贡献。
  `basis` 按实际支持程度选择；未验证的新假设不得标为 `supported`，在文本中说明推导依据和未验证部分。`evidence_ids` 引用推导依据不表示假设已被验证；探索性设想不得冒充已有贡献。
- `needs_review` 表示依赖变化后待复核，不表示结论已被证伪；原文和证据保留。
  只有显式更新依赖、证据与复核时间的结论才能恢复有效，普通采集不自动解除失效状态。

## 创新评分数据

- 当前插件的 `innovation_scores` 保存唯一评分真相，结构见 catalog Schema；评分方法仅由洞察 Skill 的[研究规范](../../dsh-plugin-insight/references/SCORING-STANDARD.md#创新评分标准innovation-v1)维护，发布输入不复制评分。
- 保存 `rubric`、固定源码 `revision`、`reviewed_at`、`status` 和 `dependencies`；technical／business 各含 criteria、score、rationale、basis、evidence_ids。分项缺失用null，任何分项为null时该轴score必须为null；其余情况下score必须等于分项和。
- 数值必须符合对应权重的档位，理由非空，引用本插件已有证据；数值轴须有可核查证据及supported／interpretation判断性质，unverified不能携带数值轴总分。评分复核时间不得晚于插件检查时间。current评分须有对应revision的源码核查证据及自身code指纹依赖，引用的依赖必须可定位。
- 评分进入分析摘要绑定；修改评分须同步当前记录的analysis摘要。新研究stage要求显式提交本轮两轴评分（允许null及缺口说明），版本必须匹配，复核时间不得早于会话截止时间。
- 依赖失效将评分置为needs_review，不自动清零、继承为新版本有效评分或重新打分；新观察省略评分时保留已有评分并按依赖判断失效。人工重新复核后才能恢复current。
- 兼容无评分的历史档案，不因加入此字段自动为历史插件补分或刷新复核时间。未评分、分项未知、版本不匹配或待复核的评分均不参与数值排序。原始评分和评分理由仅保存在JSON，不展示到读者Markdown。

## 组件推荐结论与评分

每个正式档案组件保存 `recommendation`，与 META 客观采集、创新评分分开；字段结构见 catalog Schema。研究由 AI 执行时记录 evaluator=ai，不把 AI 判断表述成人类已经审核。

- `decision` 为 unassessed（未评估）、not_recommended（不推荐）、observe（观察）、trial（试用）、install（值得安装）。不在推荐页不等于不推荐；不可从旧名单缺席推断结论。
- `reason` 用一行说明适合谁、推荐或不推荐的理由及关键条件。已评估项保存 adoption-v1 的四项 criteria（score、rationale）、总分 score、固定 revision、独立 reviewed_at、evaluator、evidence_ids 和 dependencies。推荐复核时间独立于源码检查时间，不借此刷新研究截止时间。
- 四项criteria.rationale复用已有问题回答，保存问题链接、具体材料支持、反证／未知及档位和相邻档取舍，细则见[问题到评分](../../dsh-plugin-insight/references/SCORING-STANDARD.md#从已有问题回答到分数)。使用现有字符串，不新增Schema字段；历史短理由仅兼容保留，不自动视为已按细化判据验收。
- 未评估项 reason 说明缺口，score、criteria、revision、reviewed_at、evaluator 为 null，证据与依赖为空，status=current；null 不是0。已评估项必须有完整分项、数值总分和同版本源码证据。评分方法与结论含义见[研究规范](../../dsh-plugin-insight/references/SCORING-STANDARD.md#采用推荐评分adoption-v1)。
- status=current／needs_review 表示结论有效性，不增加第六种推荐结论。当前推荐须匹配自身 code 指纹、固定分析版本与全部依赖；依赖变化保留原分和理由并置 needs_review，不自动升降级。脚本变化标记另由 META 控制暂停入榜。
- install 的引用证据必须包含同版本、带 artifact 和 environment 的 host_acceptance；高分不能绕过验收。真实安装、核心功能与禁用／卸载内容仍须逐项审阅。
- 新研究 stage 必须显式提交已评估的本轮结论、四项评分及理由，不接受 unassessed；总分由脚本求和，不能以创新分、Star、下载量或关键词推断。旧观察允许缺字段以供恢复；正式迁移逐项补 unassessed，只有已实际评估的项补分。
- 推荐对象从全部当前有效 publication.records 关联的 catalog 组件中派生，不维护独立名单；仅 current、版本一致、无待复核结论且 decision 为 trial／install 的非空评分项参与。排序与上限见输出标准。历史 publication.recommendations 仅兼容读取，当前生成器忽略，后续正式合并删除该字段；DISPLAY 不再提交名单。
- 推荐属于分析摘要；变更需同步发布记录的 analysis_sha256。仅复核推荐可使用 `snapshot assess-recommendations`，绑定正式基线及各项固定版本，持锁验证并原子合并，不改变原稿、检查时间或伪造新研究。保留档案但缺少有效发布记录的组件，只能依据已有固定版本源码证据补观察／不推荐结论及评分，并强制needs_review；不恢复发布、不将历史源码证据改标为当前版本。输入、预览及恢复见[会话操作](../../dsh-plugin-init/references/SESSION-OPERATIONS.md#组件推荐迁移与复核)。

## 观察批次与候选合并

同一固定基线可批量暂存已验收观察。批内逐项执行与单项暂存相同的校验，并验证最终合并候选；整批通过后保存 WORK，失败不保存部分检查点，不写正式快照。命令入口由列表编排 Skill 维护。

INIT 的验收过程使用[验收 Schema](../schemas/research-acceptance.schema.json)约束本轮 bundle、逐题决定与提交包，不新增正式研究字段。bundle 绑定固定 WORK 基线、输入和观察／报告／展示／计划及引用原件的字节摘要；提交包绑定 bundle 及显式审阅者、完整逐题决定、关键依赖核查和全部补充材料决定。读取和机械预检查不生成语义通过。revise 或关键依赖待补查不能暂存，材料变化后旧决定失效。暂存复用现有批量事务，在 WORK 锁内、保存前核对实际记录载荷与已审阅摘要；失败不保存部分检查点。全部已暂存且载荷一致时可回读成功，部分已暂存的批次须显式拆分剩余项。过程文件只保留在本轮，不进入正式研究真相，也不成为合并后读取或生成的依赖。

- 批次先写入本轮暂存区，提交成功检查对象的完整当前元数据；来源、证据、结论可只提交新增或复核部分。
  `findings: []` 保留已有结论，不表示删除。未检查对象不写入，失败对象进入 `errors`。
- `run_id` 唯一标识一次检查；同 ID 不得重复应用。`last_checked_at` 只在成功检查后更新，且不得晚于批次 `checked_at`，
  也不得早于档案已有检查时间。纯错误批次只追加失败记录，不改变插件档案。
- 来源移除或仓库归档保留稳定身份及明确的当前状态；超时、403、404、截断不能推断删除或不可用。
  `init` 仅适用于空档案，`update` 用于已有档案；两者均不物理删除历史条目。
- 写入必须同时满足基础档案摘要、候选结果摘要及结构约束，拒绝过期计划、损坏计划和并发覆盖。
  档案与会话写入采用独占锁和原子替换；已有锁不得被自动抢占。组件快照原子替换的临时文件使用随机标识和 `.tmp` 后缀，避免中断残留因 PID 复用阻塞重写；新旧临时命名均不进入 Git，事务撤销仍以 `.transaction/` 为准。

## 持久受阻与重试

- 正式快照可含 `research_blocks` 映射，按稳定组件ID保存最近一次受阻，独立于完成研究档案和发布记录。旧快照没有此字段等价于无已登记受阻，不强制改写历史。
- 每项按受阻Schema保存 `plugin_id`、固定 `revision`（未知为null）、稳定 `reason_code`、可读 `reason`、自包含 `details`、`blocked_at` 与登记轮次 `run_id`。详情保留问题文件、错误/必要字节事实、固定版本出处和下一步，不只引用本机runs路径；不保存凭据。原因代码描述稳定故障类别，不以时间、原始报错措辞或轮次生成新代码。
- block先写本轮所选条目的 `block` 及blocked状态，最终plan/apply与研究成果一起持久化；全轮只有受阻记录也可合并，不伪造成功研究。失败不覆盖已有有效报告/展示；后续成功stage并合并才清除该组件的旧受阻。新版本再次失败则替换为新版本原因，历史由Git追踪。
- 新轮次候选的非空代码版本与正式受阻版本相同时，沿用已知原因，默认放入 `selection.suppressed_ids`，不准备材料、不调用洞察、不占额度。只有目录、热度或报错描述变化不触发重试；未重新处理不能声称已确认故障消失或原因变化。未知版本不作同版本去重。
- 版本变化恢复正常增量候选资格，仍按额度和顺序选择。用户明确要求重试时，`snapshot start --retry-plugin <稳定ID>`（可重复）固定 `selection.retry_ids`，指定项优先、去重后占正常额度，超额度或非已登记受阻候选则拒绝；不能用重试扩充额度。相同版本的环境/统计器修复也通过显式重试处理，不每轮自动试探。
- 同轮恢复保持固定选择和跳过集合；仅用户明确要求时可用 `snapshot retry --work ... --plugin ...` 将尚未合并的已选blocked项重置pending，删除本轮block后重新准备，保留原始失败文件。未选/已完成项不接受retry；已合并轮次通过新轮显式重试，不修改旧事务。
- 选择绑定正式快照摘要与上述跳过/重试集合；合并时重新计算核对，不允许随意填入跳过ID绕过研究。已知受阻跳过数量、本轮受阻数量和完成数量分别报告；跳过不算完成或本轮失败。

## 本轮会话与检查点

- 会话 `id` 标识本轮增量，`checked_at` 为本轮检查基准时间；新轮次绑定当前快照摘要，同轮续跑保留选择和完成材料。
  现有 `previous_digest` 仍表示旧实现中的对照会话摘要，不能冒充当前快照摘要；它不再是新流程必须提供历史会话的理由。
- 会话输入从固定版本的目录条目生成；YAML／Markdown 解析、仓库数字 ID、规范仓库名、组件路径及目录条目摘要都须可追溯。
  GitHub 重定向或改名按数字 ID 合并，不能把同一仓库的旧新名称当作两个对象；组件 ID 优先复用当前档案中同一数字仓库和路径的既有分配。
  新路径规范化得到的组件 ID 若已分配给同仓库其他路径，必须记录问题并停止分配，不能推断为组件移动。
  无法解析条目、核实身份或确认默认分支时保存问题记录，并将受影响来源视为不完整，不静默漏项或据此推断移除。
- 来源 `complete` 表示本轮范围内完整读取，不表示插件可用；未知来源／代码 `revision` 为 null，不能编造版本。
  候选的 `source_urls` 必须对应会话来源，身份、路径与指纹保持可追溯。
- `changes` 中 added 表示当前基线没有该身份；moved、content_changed、sources_changed 分别表示位置、内容指纹和来源变化。
  无变化为 unchanged，不能确认则为 unknown。仅当基线中相关来源已知且本轮均完整核查且候选缺席，才可标记 removed_from_source。
  缩小范围不算生态删除；变化标记可重叠，不能相加为对象总数，完整研究资格须结合下述轻量更新规则判断。
- 新轮次使用 `selection.mode = incremental`，将基线中已有完成研究记录（含保留完整研究原稿、因失效退出当前展示的项）的 ID 固定在 `selection.researched_ids`，其中结论已失效或尚未恢复当前展示记录的待复核 ID 固定在 `selection.review_required_ids`；两者必须与正式基线一致。目录中已发现但从未完成研究的条目仍是新研究项。
  先比较全部已有成果与本轮输入；源码版本变化、路径迁移、缺席无法确认、指纹未知或依赖失效的已有项进入更新队列（INIT 的频繁更新过滤适用时暂缓版本更新）；仅目录／维护信息变化按轻量更新规则处理，确认未变的已有项保留原成果且不占额度。比较基线取该项最后完成研究的记录，不能取后来只发现而未完成研究的版本。
  先排除正式同版本受阻项，将显式重试项按输入顺序置前；新轮将更新队列和尚无完成研究记录的新项分别按下述综合热度排序，依次补入并固定 `selected_ids`。缺少 selection.heat 的历史会话保留完整输入顺序（缺席更新项追加其后），不按新规则重排。
  `research_limit` 表示更新与新项的总额度，必须为正安全整数；新调用省略参数时默认40，并在新会话中显式保存40。历史会话未保存额度时保持原有选择语义，不在恢复时套用新默认值。额度40、待更新 n≤40时补充最多40−n个新项；n>40时先做40个更新项，剩余更新留待后轮。新项不足时允许少于额度。
  `selected_ids` 在增量模式总是存在（允许空数组）；`selectedItems` 按固定选择顺序返回。未带 `selection` 的既有会话继续按旧的前 N 项语义校验和恢复，不反写历史选择。
  本轮选中后首次受阻的项仍占名额，续跑不补位、不重置；正式同版本受阻在选择前跳过，不占新轮名额；未选项保留 pending，但不接受完成、受阻或重试状态变更。
- 新会话条目从 pending 开始；blocked 带受阻原因，complete 必须带检查点。
  所选范围的 complete／blocked／total 与完整列表 listed、未选 deferred 分开统计，不能把未选条目称作已研究。
- 检查点绑定本轮已暂存并验证的观察批次、运行 ID、固定版本与材料摘要；候选档案必须匹配提交的指纹、证据和检查时间。
  本轮结论须显式复核，时间不早于会话基准，并有对应版本源码证据；时间较新本身不证明研究已完成。
  无固定版本或无源码核查不能成为 complete，材料不存在或摘要不符即失效，不得静默覆盖原件。
- start 后的会话候选、来源、指纹和选择属于本轮固定事实。暂存候选若与会话不一致，应诊断观察批次或输入错误，
  不得把当前档案指纹反向写回会话来通过 checkpoint。只改变格式的历史修复走显式迁移，不复制旧会话并伪造新的检查时间或研究轮次。
- 会话完成表示本轮记录已准备好，最终合并状态另行回读确认；不表示目标插件验收通过。只读队列选择不提供并发认领语义。

本轮会话、观察批次和准备材料存放在 Git 忽略的 `data/runs/`，用于合并前恢复。新流程的当前快照必须包含持续使用所需的分析和证据，不靠历史会话证明其有效性。
历史 manifest 只用于首次迁移或可选审计；当前生成器、校验和新轮次均只依赖正式快照。记录完成时仍验证本轮检查点，合并后不需要 runs。

### INIT 版本更新暂缓集合

过滤策略定义在[列表编排 Skill 的频繁更新过滤](../../dsh-plugin-init/SKILL.md#频繁更新过滤)。新会话的可选 selection.cooldown_ids 保存按正式基线与本轮固定 checked_at 计算的近期版本更新候选；入队前还需将输入与最后研究基线比较：非 code 指纹变化若被任一现有结论、创新评分或采用推荐声明依赖，则排除出暂缓集合，不等待 catalog 先变为 needs_review；仅 code revision 变化仍遵循 INIT 的过滤策略。已有 review_required_ids 和显式 retry_ids 优先，suppressed_ids 仍代表同版本受阻，不混用原因。合并重算该集合并校验摘要，不修改旧会话选择。本轮 INPUT 保存实际 revision；暂缓不刷新研究基线、报告或证据，不表示新版本已完成研究。窗口跳过数按未入选且未被同版本受阻抑制的 ID 单列。

### 综合热度与固定队列

综合热度 `heat-v1` 只用于 INIT 的候选排期，不是研究结论、创新分或采用推荐。新轮在截断额度前排序：显式重试优先，已有更新项其次，首次研究项补足额度；更新与首次研究两组各按热度降序，同分按稳定 ID 字节序。冷却、受阻、轻量更新资格不因热度改变。旧 WORK 没有 `selection.heat` 时按原顺序恢复，不反向升级历史选择。

冻结会话全体候选的可用 Star 最大值 `Smax` 和近30日下载量最大值 `Dmax`，对各项已知值分别计算 `s=ln(1+S)/ln(1+Smax)`、`d=ln(1+D)/ln(1+Dmax)`；最大值为0时，该项已知零的归一化值为0。两项都已知时 `H=100*(s+d)/2`，只有一项时 `H=100*s` 或 `100*d`，都未知时 H 为 null 并排在所有有数据项之后。这个分数是本轮相对热度，跨轮分数不能直接比较；单指标与双指标的覆盖差异必须保留，不将缺失补0。

Star 按稳定仓库 ID 读取 Git 缓存，下载量只按当前正式 META 中最后核实的精确 npm 包名读取 npm 缓存。字段组缺失时允许使用本轮开始时的正式 META，但成功采集时间同样必须不晚于截止且不超过24小时，下载窗口必须覆盖截止前30个完整UTC日。Star 的正式 META 时间优先取 git_cache.captured_at，不以较新的顶层采集时间延长缓存寿命；已知仓库 ID 冲突时也不能借用该 META 的 npm 包名。缺少包名的候选只评估 Star，不因仓库下其他组件的包名关联猜测自身身份。

同仓库多个组件共享 Star，同包多个组件共享下载量，分别引用同一指标而不相加；重复引用不会增大归一化最大值。热度取值不代表用户数或质量，也不创建对未研究插件的正式成果。

`selection.heat` 保存版本、截止时间、正式基线摘要、逐项原始值／成功时间／包名／字段来源，以及固定 Git commit/blob 和 npm blob、缓存读取错误；无指标用 null。分数由冻结值确定性重算，不单独人工填分。CLI 开始新轮固定远端缓存；直接调用 startWork 未提供外部缓存时仍以正式 META 固定本地热度。外部缓存失败不会逐插件无预算回源，保留错误并退化到新鲜正式 META 或未知。startWork 持锁核对热度的正式基线摘要，期间基线变化必须重新采集，不把旧热度套入新基线。

会话校验核对热度范围、时间、来源和选择顺序；WORK 摘要绑定热度。恢复、stage、plan 和 apply 均使用该冻结值，不依据墙上时间或后续 META 刷新重排；合并仍重新核对原有资格和正式基线。只保存于本轮过程，正式研究、来源指纹、评分和页面排序不受影响。

### 目录与维护信息的轻量更新

新建快照会话固定 `selection.metadata_only_ids`，合并时从正式基线重算核对。仅已完成研究、固定源码 revision 与仓库／组件路径不变，且指纹差异仅在 directory、maintenance（也允许仅来源成员变化）的候选可进入该集合；未知、迁移或目录移除不适用。若任一现有结论、创新评分或采用推荐声明依赖变化的字段，则保留完整研究资格；已有 needs_review 和显式 retry 也优先。轻量项不占研究额度、不准备源码材料、不重写报告或证据包。

本轮 INPUT／WORK 保存来源成员及最新指纹；catalog 的 fingerprints、checked_at、analysis_sha256 与证据保持最后完成研究的基线，不能用 META 采集冒充研究复核。合并后如需更新维护指标，通过 `refresh:meta -- --plugin <稳定ID>`（可重复）定向刷新 META；不要在固定事务合并前改写正式基线。旧会话缺少 metadata_only_ids 时继续按原选择语义恢复，不反写选择。

新生成的 REVIEWED-SOURCE.json 仅保存固定提交源码、问题证据与 inventory，不嵌入 META；META 独立保存在同组件 meta.json，并由兼容逻辑 metadata 字段及 publication.metadata 引用。旧证据包内已有 metadata 仅作历史采集材料兼容读取，不作为当前 META 真相源，不为拆分而批量重写旧包。源码 revision 改变按研究资格与 INIT 的频繁更新过滤决定是否入队；此规则不声称仓库提交变化但局部文件相同即可免研。

## 发布输入、META 与统计字段

- 发布输入只组织已有成果，不成为研究事实或结论的替代真相源；推荐对象由已完成项的组件推荐结论派生。
  `metadata` 以稳定插件 ID 关联快照，仓库数字 ID 和名称必须匹配；`history` 兼容旧输入。
  现有可选 `catalog` 与 `history` 字段仅兼容旧输入，不作为新流程的历史依赖；首次 added 仅表示本工程入档，不代表 npm 发布。
- 发布输入 `summaries` 按插件 ID 绑定作者功能材料的归纳文本、来源 URL 和固定版本；它不是独立验证结论，也不冒充逐字引文。
- 发布输入 `capabilities` 绑定固定版本的人工确认能力条目；省略项不表示已确认数量为零。
  装配输入 `ANALYSIS.capabilities` 对应发布输入 `capabilities[plugin_id].items`，是按扩展类型分类的对象，不是任意功能名或数组。允许键仅为 `Skill`、`Agent/Preset`、`模型工具`、`用户命令`、`Host 路由`、`界面`、`事件监听`、`后台`；每个值是非空、无换行的字符串。只填写已确认项，未确认类型省略，不补零。按具体用户功能组织的名称、用途及边界写入 `capability_table`，不能作为摘要对象的新键；表格不豁免摘要校验。
  装配器与暂存入口通过共享校验器复用发布 Schema 的 summaries、capabilities、advice 单项结构，META 复用既有元数据校验。装配在写出 REVIEWED-SOURCE、INSIGHT、OBSERVATIONS、DISPLAY 前完成全部字段校验；失败报告字段路径、类型要求或允许键，不生成本次交付文件。字段校验不替代暂存时的身份、版本、证据和检查点验收。
- 发布输入 `advice` 是按插件 ID 保存的读者版使用建议；`revision` 必须与研究提交一致，`text` 只润色表达，不改变证据事实或当前结论。
- META 的 `captured_at` 是采集时间，`pushed_at` 是仓库推送时间，两者不能混用。
  缺失／失败值为 null 并保留错误，不用 0 代替未知；GitHub 与 npm 各自时间及窗口独立保留。
- 可选 `npm` 绑定已核实的 `package_name`、下载量、窗口、来源与错误；缺少该对象不等于下载量为零。
  返回包名、窗口与非负整数下载数须匹配，否则记未知；下载量不等于用户数。
- `npm.publication` 的 first_published_at 来自已核实包的注册表 time.created，表示首次发布，仅保留为数据。可选的 latest_version、latest_published_at、latest_error 必须成组出现，来自注册表 dist-tags.latest、该版本的 time[version] 及版本条目身份核对；不是 time.modified、任意最高版本或 Git 推送时间。成功时版本与日期同时存在且 latest_error 为 null，失败时两者为 null 并保存错误。首次时间与最新版本采集可独立失败；旧快照缺少 latest 字段时视为未知，不回退首次时间。采集时间及注册表来源共用 publication.captured_at／source_url，缺失或失败不从入档、Git 或下载量推断。
- `refresh:meta -- --npm-publication-only` 仅重采既有已确认包名的 publication，保留下载、GitHub指标、脚本更新检查、研究记录与推荐，仍经基线摘要、完整校验、独占锁及原子快照写入；默认每日完整META刷新也采集最新版本字段。
- META 采集开始时先从私有 `thundax-lyp/dsh-plugin-meta` 仓库回读一次固定的 `main:data/NPM-META.jsonl` blob，并对整份 JSONL 的包名、排序和已出现字段做校验。同次运行只使用该 blob，不在组件之间追随移动分支头。
  对已有已核实 `npm.package_name` 的组件，近30日下载量和发布信息分别按字段组查找外部记录：记录的成功 `checked_at` 不得晚于本轮采集时点且不超过24小时；下载字段组还必须精确覆盖本轮采集时点之前30个完整UTC日。满足时保留记录自身的 `checked_at` 作为 `captured_at`；记录不存在、过期、窗口不匹配、失败记录没有仍新鲜的旧成功值或字段组不完整时，才回源 npm downloads／registry。外部缓存读取失败时记录缓存错误并回源，不把失败当成空值或零。包级缓存不保存组件对应的 GitHub 仓库指标，因此仓库身份、Star、Issue、推送时间和代码更新检查仍在需要时访问 GitHub 仓库接口。缓存值进入正式 META 前继续通过本工程 Schema 校验，不改变 npm 包名必须先由源码核实的身份边界。
  `prepare:selected` 与手动 `refresh:meta` 使用同一缓存解析和字段组判定；前者在任何选中项 META 采集前固定远端 blob，并在本轮 `PREPARATION.json` 保存仓库、分支、路径、blob SHA、缓存错误及每项下载量／发布信息的实际来源。缓存命中不得再请求对应 npm 接口；缓存下载量完整而发布信息不完整时只回源 registry，不能重复请求 downloads。
- Git 仓库指标缓存独立读取 `data/GIT-META.jsonl` 和 `data/GIT-ERRORS.jsonl`，两者必须绑定同一完整远端 commit SHA；同次 prepare:selected 或完整 refresh:meta 仅固定读取一次，不逐组件追随分支。整份 JSONL 校验字段、正整数 ID、数值排序、非负 Star、布尔归档状态及完整 UTC 时间戳（拒绝仅日期与非法日历日期）；未知字段、重复 ID 和不完整记录导致缓存读取失败并显式回源，不视为零。
  已核实稳定 ID 对应的成功记录时间不得晚于本轮采集时点且不超过24小时，满足才复用 `stars` 和可选 `archived`。零 Star 与 false 归档状态都是有效值；改名按 ID 匹配，不按仓库名匹配。存在失败记录但旧成功值仍新鲜时可复用，保留 `latest_error`，不能以失败尝试时间延长成功值有效期。
  命中时在 META 的可选 `git_cache` 中保存原成功 `captured_at`、缓存来源仓库、路径、固定 commit SHA、指标与错误 blob SHA 及最新错误，顶层 `captured_at` 仍代表本轮采集，不能用它冒充缓存 Star 的新采集时间。缓存缺失、过期、未来时间或身份不匹配时回源 GitHub；已知 ID 的仓库查询使用 `/repositories/<id>` 并核对返回身份，身份冲突直接拒绝，不用缓存掩盖。
  当前 Git 缓存不包含 `pushed_at`、Issue 统计或代码更新信息；这些继续直接查询 GitHub，因此缓存命中不意味着完全取消仓库接口请求。仓库接口失败但有新鲜缓存时保留 Star、归档状态和错误，缺失的推送时间及 Issue 统计保持未知，不继续按可能过期的名称查询 Issue。publication-only 刷新不读取或更新 Git 缓存。
  prepare:selected 在本轮 `GIT-META-CACHE.json` 只落地无令牌的固定缓存副本供采集子进程使用，并在 PREPARATION 保存缓存来源、commit/blob、错误及逐项字段来源；完整 refresh:meta 的结果同样报告字段来源和缓存错误。缓存副本属于可保留的本轮过程，不写入源码证据或研究结论。
- 可选 `code_update` 绑定研究基线、当前提交、变更路径和核查时间；`script_changed` 为 true／false／null 三态。
  它表示待重新洞察的脚本变化，独立于 findings 的依赖失效状态，不改写研究深度或完成检查点。
- 工程统计的 `revision`／`component`／`coverage` 界定版本、组件及完整或抽读范围；工具版本、内容摘要与排除项须保留。
  静态能力候选不是正式能力数，`confirmed_count: null` 表示未确认，不能转成 0；统计材料同样不可覆盖检查点已绑定的原件。

### 外部 META 双清单回写

私有 GitHub 仓库 `thundax-lyp/dsh-plugin-meta` 分开维护 npm 与 GitHub 采集对象和指标。INIT 收尾使用
`npm run export:meta-manifests -- --work data/runs/<round>/WORK.json` 预览两份清单，再以 `--apply` 同步；原 `export:package-manifest` 只更新 npm，保留作单清单工具，不能替代 INIT 完成条件。不得依赖相邻 checkout 或直接写入其他工作区。

- `data/NPM-MANIFEST.jsonl` 每行只有 `{ "package": "<npm-name>" }`，按完整包名字节序去重排序。`data/NPM-META.jsonl` 为独立指标缓存。
- `data/GIT-MANIFEST.jsonl` 每行包含 `repository_id`、`node_id`、`repository`、`npm_packages`、`source_repositories`，按正整数 `repository_id` 数值升序去重。`repository` 保存仓库名称，`node_id` 供批量采集固定对象，`source_repositories` 是小写来源仓库名称数组；同仓库多个组件及改名后的来源归入同一 ID。`npm_packages` 是包名关联数组，空数组只表示无已核实包名。所有数组去重并按字节序排序，同一来源名称不能同时归入不同仓库 ID。
- `data/GIT-META.jsonl` 由目标工程独立采集 Star 等仓库指标。回写只更新两个 MANIFEST，不写 npm／Git 指标、待解析或错误文件，不触发采集工作流。

WORK 通过共享过程读取器和校验器读取；INPUT 的 `plugins` 是该轮来源扫描中通过仓库身份和默认分支核实的完整组件集合，不能用已研究 catalog 数量替代。Git 候选从每个组件的稳定 ID 提取仓库 ID，并与存在的 INPUT metadata.repository_id 交叉核对；不因缺少正式 META 排除仓库。已有远端 ID 复用其 node ID，新 ID 通过 GitHub `/repositories/<id>` 核实数字 ID、node ID 和当前名称后才能写入；身份查询失败即阻止整次同步，不能伪造 node ID 或静默漏项。

当前固定目录源码及 INPUT 不提供 npm 包名字段；上游在线目录可提供，但不是本轮固定 INPUT 的身份依据。回写只联结正式 catalog META 中已有的精确 `npm.package_name`，同时用于 npm 清单和 Git 的包名关联；没有正式 META 或没有已核实包名的组件分别计入缺失，不从仓库、组件、目录名称或描述推断。目标工程独立导入的已有包名、仓库和关联全部保留，不以本轮缺席推断删除。

两份输出分别为“远端已有 ∪ 本轮已核实”的追加合并；必须报告完整组件数、具有来源包名字段的组件数、已核实包名组件数、唯一包名数、两类缺失数，以及 npm／Git 的远端已有、本轮已存在、新增、保留历史、删除数0和最终输出数。Git 另报告本轮唯一仓库数。来源扫描失败、INPUT 不包含的未解析条目不冒充已覆盖；不得将已核实 npm 子集表述为全量包覆盖。

预览先固定远端分支完整 commit SHA，并从该提交读取两个 MANIFEST，目标文件缺失时停止，不回退旧路径或自动初始化。`--apply` 使用 Git Data API 基于该提交创建只包含变更清单的 tree 和单个 commit，以非强制分支更新防止覆盖并发提交。无内容变化则不创建提交。写入后从分支最新的同一固定提交回读两个文件并逐字节核对，任一不匹配均报告受阻、保留 WORK，先重新预览再恢复；不能凭提交 API 返回值判定完成。最后再运行只读命令，确认两份 `changed: false` 后才进入清理。

省略 `--work` 仅在 `data/runs/` 中恰有一个 WORK 时允许。认证使用 `GH_TOKEN`、`GITHUB_TOKEN` 或本机 `gh` 登录，目标写入需要对应 Contents 权限并遵守分支保护。Skill 收尾授权只覆盖 npm／Git 两份清单的单个远端提交，不授权部署或改名目标工程文件、修改指标和 CI、推送本工程、创建 PR 或触发消费方刷新。包名或仓库错误、迁移和退役走独立显式清理，不由普通 INIT 裁剪。

## 路径、兼容与清理

- 稳定身份与物理目录分离，路径注册表使改名／移动不改变当前入口；轮次目录只标识本轮工作区。
- 未完成增量的证据、报告和检查点不能静默覆写。需要修正时先解除该项完成状态并重新校验，不能只刷新摘要掩盖内容变化。
  `snapshot reopen` 仅解除尚未合并的已选 complete 项：输入绑定旧暂存记录的完整语义摘要并说明原因，持 WORK 锁核对正式基线及完整检查点，先保存旧记录、证据和条目备份，再将该项改为 pending。固定身份、版本、选择、额度及检查时间保持不变，其他项不变；不适用于 blocked 重试。修订后重新 prepare、逐题验收及 stage，旧决定不授权新字节。默认只预览，显式 `--apply` 才写入。
- 已合并记录的后续变化通过新增量替换当前状态，旧状态可由 Git 查询；不要求重新创建旧轮次或保留所有本地原件。
- 清理前检查当前引用、未合并状态与活动锁；当前仍引用的材料先迁入正式位置并校验，再清理过程副本。
- 旧迁移记录及清理脚本仅适用于其原有归档格式。适配新模型前不得用旧工具扩大删除范围，也不得删除现有材料来绕过校验。更新规范本身不执行数据迁移。

## 逐题研究材料与正式报告

新单插件装配输入的 research_questions 由[问题交付 Schema](../schemas/research-questions.schema.json)约束，研究执行以[逐题流程](../../dsh-plugin-insight/references/QUESTION-WORKFLOW.md)为准。它是研究输入与过程结构，不新增 catalog 字段，不改既有分析摘要或身份。逐题完整回答、固定版本证据定位与原文写入正式 reports；完整 research_questions（含 status 和全部 unknowns）随 REVIEWED-SOURCE.json 材料包进入正式 artifacts，读者展示过滤不改变持久化内容。源材料仍通过 artifacts 保存。主题覆盖、文本、ID和源码位置可机械校验，论证充分性与结论真实性须逐题审阅。

已合并的当前研究不能依赖 PLAN、逐题本地文件或 ANALYSIS 存在；清理过程副本前验证正式报告和必要证据足以独立回读。历史报告缺少逐题结构时保持原状态，不从旧摘要补造研究，不因展示重生成升级研究深度或验收状态。

## 能力表格的展示绑定

发布输入 capabilities 的 revision、items 继续保存同版本的正向能力摘要；可选 table 保存研究者据实际源码撰写的 Markdown 能力表。table 须与正式原稿“能力清单”唯一章节的正文一致，生成前核对，不能从摘要自动推导使用条件或边界。历史输入不含 table 时继续核对原列表；版式变更不刷新研究时间、证据层级或评分。展示列及编写要求由[输出标准](../../dsh-plugin-init/references/OUTPUT-STANDARD.md)维护。

## 逐题缺口与范围说明

逐题 unknowns 的可选 kind 按研究问题 Schema 区分实际研究缺口 research_gap 与本轮未安排的工作 scope_boundary，省略时视为 research_gap。分类由研究者给定，不改变 status 验收或证据层级；读者正文只列实际缺口，范围说明仍保存。呈现要求见输出标准，字段解释与填写流程见逐题研究规范。

## 显式丢弃研究

用户明确要求从头重建时，可按稳定 ID 和快照摘要显式丢弃指定组件的研究与发现记录。此操作通过快照事务执行，不从 pending/blocked 自动推断；同时移除依赖被删组件的交叉 finding，并将这些 finding 所属组件移出当前 publication.records，保留其原报告和展示输入供重新复核，不为未同步的旧报告重绑分析摘要。未受影响的发布记录及其摘要保持不变。其他组件的评分与必要原文证据保留并重新校验，不能通过删除依赖字段伪造有效性。原报告和数据的历史可从 Git 追溯，后续列表 Skill 可重新从目录来源发现组件。操作入口由列表编排 Skill 维护。
