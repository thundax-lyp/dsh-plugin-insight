# 单插件洞察

目标是说明：谁用它完成什么任务、相比原办法改变了什么、哪些条件使价值不成立，以及下一步值得验证什么。先逐题核查，再综合；装配与结构校验不能代替研究判断。

## 执行边界

- 本 Skill 由子 Agent 执行。用户独立调用时，父 Agent 核实输入并分派；整轮调用沿用父 Agent 固定的队列。子 Agent 不再委派。
- 只读分配的组件与固定提交，只写独占本轮目录。父 Agent 验收并串行 stage；子 Agent 不改共享 WORK／SESSION、正式快照、README 或其他组件，不执行 plan／apply。
- 不自动安装插件、运行目标代码、启动付费实验、提交或发布。运行证据只记录实际发生的执行，不把源码核查写成运行通过。
- 命令在工程根执行，Node 版本遵循 `.node-version`；Git 协作遵循根 AGENTS。单独调用不因发现会话而自动入档或完成队列。

## 按阶段读取

| 阶段 | 读取依据 | 使用目的 |
| --- | --- | --- |
| 开始 | [研究规范](references/RESEARCH-STANDARD.md)、[逐题流程](references/QUESTION-WORKFLOW.md) | 确定证据层级、研究问题与完整交付 |
| 核查每题 | 研究规范中该题对应的 QUESTION 参考 | 只加载相关方法，不将主题表当固定问卷 |
| 形成结论 | [评分标准](references/SCORING-STANDARD.md)、[具体用法](references/QUESTION-ADOPTION.md#最值得推荐的具体用法) | 从已有回答独立推导创新与采用判断 |
| 写结构化输入／装配 | [分析输入与装配](references/ANALYSIS-INPUT.md)、[数据契约](../_shared/references/DATA-CONTRACT.md)中的身份、证据、结论与发布字段 | 填写现有字段，校验版本和来源 |
| 交付／成品检查 | [输出标准](../dsh-plugin-init/references/OUTPUT-STANDARD.md)的逐题交付、报告结构、成品语言与详情展示 | 保留论证和边界，检查读者实际看到的内容 |

读取长规范时先按标题定位当前任务的章节，再分段读正文；不要把全部规范、问题参考和 SOURCE 正文拼成一次大输出。工具返回截断时补读缺失部分，不能把截断内容计为已检查。

## 1. 核对输入与材料

取得稳定组件 ID、注册 slug、仓库／组件路径、完整提交、检查时间、目标深度、独占输出目录，以及当前同版本分析、证据与依赖。检查时间是材料的基准时间，不是任务执行截止时刻；不据此省略研究。

已有 `INVENTORY.json`、`MATERIALS.json`、`META.json`、`SOURCE.json` 时，核对身份、版本和摘要后复用。材料不足时只补查影响判断的部分；checkout 必须固定且干净，不执行目标代码。缺少身份或固定版本先核实，不编造 ID。没有活跃 WORK 的独立调用由父 Agent 处理事务入口，子 Agent 不伪造会话字段。

未准备材料时，先用 `npm run inventory:plugin -- --root <readonly-checkout> --ref <commit> --component <path> --out <dir>/INVENTORY.json`，根组件省略 component。只有抽读快照时使用 `--snapshot` 并注明子集，不能报成全插件 LOC；统计与能力确认按[工程方法](references/QUESTION-ENGINEERING.md)。再用：

```sh
npm run prepare:plugin -- \
  --session data/runs/<round>/SESSION.json --plugin <id> \
  --checkout <readonly-checkout> --inventory <dir>/INVENTORY.json \
  --out <dir>/MATERIALS.json
```

有目录原件时可重复传 `--directory-entry <file>`。准备器只生成材料索引，不形成 observation、finding 或研究结论；身份／提交／组件不一致时停止。META 与源码证据分开；缓存和独立 `--repository-id` 参数按[数据契约](../_shared/references/DATA-CONTRACT.md#发布输入meta-与统计字段)处理，不用 Star 缓存替代源码、Issue 或推送时间核查。

## 2. 列问题并逐题核查

在 `<dir>/PLAN.md` 先写总目标、稳定问题 ID、主题、材料线索与回答判据。九类主题均映射到具体问题；题数按复杂性决定，可合并确有共同论证的主题，不新增统一问卷。发现新线索可增补，保留已有 ID。

每题独立保存 `<QID>.md`：直接回答 → 支持与反证 → 固定证据位置及关键原文 → 未知项、影响与下一步 → 状态。`partial`／`unknown` 必须说明缺口；不适用须说明原因。按[逐题流程](references/QUESTION-WORKFLOW.md)填写完整 `research_questions`。

优先核查会改变贡献或采用结论的主张：

- 对照原生能力、上游与简单替代，区分作者主张、继承能力及本组件的实际贡献。
- 沿实际入口、调用、状态变化跟到用户可见结果；核对关键失败分支，不以静态候选、接口定义或函数名代替实际接线。
- 围绕该主张解释依赖、兼容、用户／后台／异常流程及首次、持续、失败恢复成本。现金与人工时间分开；未知不填0，不推算未测收益。
- 区分确认缺陷、设计取舍、未验证风险和材料缺口。固定源码能支持机制判断，不能证明外部服务可用、任务效果或真实需求。

Git 引用绑定原始仓库、完整提交、路径与有效行号；非 Git 材料保存必要原件和上下文。证据原文与程序标识符不为润色而改写。

## 3. 验收回答，再形成判断

对照 PLAN 逐题检查充分性和跨题冲突，再写贡献、关键质疑、采用结论与未验证假设，均回指实际 `[Q01](#research-q01)` 等问题。关键材料完全不可查或不能形成自包含报告时返回受阻；有边界的未知可交付，但不能与采用建议矛盾。

- **贡献与假设**：检查参照、归因、反例和其他解释。新方向说明推导依据、相对增量、最小验证与推翻条件；没有依据时写明未形成，不强凑创新，不计入插件已有贡献。
- **创新评分**：按 innovation-v1 分别评技术和业务；分项、参照、限制和性质存 JSON，不写入读者报告。
- **采用判断**：按 adoption-v1 从已有回答推导 decision 与四项分数。每项理由含问题链接、具体材料、反证和相邻档取舍；源码级 evidence 的13分是上限而非默认值。先独立判断再对照旧分，不按热度、题目状态或总分阈值升级结论。
- **推荐理由**：三句自然完整的话分别说明谁做什么、比原办法多做成什么、何时停止及退路；理由仍为单行字符串。使用建议补操作，不照抄三句理由。

所选更新项完整复核 findings，不用空数组继承旧点评。旧证据只有版本、环境和范围匹配才复用；报告只表达当前状态，不写旧稿差异。仅推荐复核或 META 刷新由父 Agent 走对应事务，不伪造新研究及检查时间。

## 4. 保存、装配与检查成品

按[分析输入与装配](references/ANALYSIS-INPUT.md)填写 `ANALYSIS.json`，使用现有命令装配 `INSIGHT.md`、`OBSERVATIONS.json`、`DISPLAY.json` 和 `REVIEWED-SOURCE.json`。不以通用段落批量生成语义，不改 Schema 绕过错误。额外证据、真实执行与跨组件依赖按契约显式提供，不能伪装成源码证据。

报告须保留完整逐题回答及证据；四标签原稿、能力／依赖／步骤／成本／效果表、长短篇组织和证据折叠按输出标准交付。引用块、编号、目录与 META 是展示层职责，不手工改生成页面或研究时间。完整问题对象随 REVIEWED-SOURCE 进入正式 artifacts，不能只留过程链接。

从实际报告上下文检查三件事：读者能否理解用途、贡献与主要限制；建议是否具体可做并有退路；正文是否补充短评而非重复。技术术语解释作用，中文与名称适当留空格，检查连续表格、标题、加粗和链接。保留否定、条件、未知项及证据原文，不按相似度删论证；具体版式以[成品语言与排版](../dsh-plugin-init/references/OUTPUT-STANDARD.md#成品语言与排版)为准。

## 5. 返回父 Agent

交付以下内容，不能只报“装配成功”：

- 稳定 ID、完整提交、真实条目类型、实际研究深度、完整 PLAN／问题／报告／观察／展示输入及证据路径。
- 项目自身描述支持的功能摘要（最多80字符，带来源 URL 与版本）、固定版本正向能力清单；未确认数量不填0。
- 贡献、关键限制、采用条件、未验证项与错误。受阻时保存稳定 reason_code、可读原因、自包含问题详情和下一步，由父 Agent 登记。

父 Agent 对照计划逐题验收、校验观察和依赖后才 stage；子 Agent 回报不表示已入正式快照或通过宿主验收。当前快照能独立生成并且无引用后，父 Agent 才可按规则清理过程副本。
