# 逐题研究与综合

本文件定义一个插件研究任务如何拆分、完成和综合；具体核查方法由[研究规范](RESEARCH-STANDARD.md)的研究问题表路由，读者输出以[输出标准](../../dsh-plugin-init/references/OUTPUT-STANDARD.md)为准。

## 先定总目标，再列问题

输入为固定插件身份、版本、材料范围和研究目标。先以一句完整问题表达总目标，写入本轮 `data/runs/<round>/questions/<plugin-slug>/PLAN.md`，再列带稳定 ID 的具体研究问题：`Q01`、`Q02`……。计划表至少列 ID、问题、对应主题、已有线索、拟检查材料和回答判据；已知未知项同步列入。不能先写综合摘要，再把摘要分段贴上问题标题。

题数按插件复杂性和问题独立性决定，不规定每个插件相同的N；一道问题应能形成独立、可核对的回答，不能用一道“综合评价”替代分解。场景、机制、贡献、限制、依赖、成本、工程、假设、采用九类主题须分别映射到问题；可由同一道确有共同论证的问题覆盖相关主题。某主题不适用时以对应问题的 not_applicable 状态解释原因，不默默跳过。发现新线索可增补问题、记明原因，保留已有 ID，不反向改计划来掩盖未完成。

## 每题形成完整交付

本轮每题独立保存为 `questions/<plugin-slug>/<QID>.md`，可以共享采集材料，但必须逐题建立证据与结论关系。每题包含：

1. **明确的问题与判据**：范围、对象、比较基线以及什么材料足以回答。
2. **完整回答**：先给直接回答，再展开事实、机制或比较、解释与反例，说明结论何时成立。不能只交一句结论、四标签短评、功能摘要或指向别题的链接。
3. **证据**：具体版本、来源位置、关键原文或观察，以及它支持或限制了回答的哪一步。作者声明、源码检查与运行结果分别表达；材料数量不等于证据充分。
4. **未知项**：缺什么、影响哪项判断、下一步如何取得可支持或推翻判断的证据。无未知项时显式记录空清单，不以空白冒充完整；不适用也须解释。
5. **状态**：answered、partial、unknown、not_applicable。partial 与 unknown 必须有未知项，answered 和 partial 必须有证据。unknown 是完整交付了一个“当前不能回答”的结果，不是已证实无效或偷偷跳过。

未来设计假设必须明确未验证状态；它可能有推导依据，但不能因问题状态为 answered 就变成已实现能力。没有授权不运行插件、安装软件或安排付费实验；可交付有依据的未知结论和下一步方案。主题级论证在本插件既有研究 Agent 内完成，不因拆题自行扩展多 Agent 委派。

## 结构化装配接口

`ANALYSIS.json` 的必填 `research_questions` 结构以[问题交付 Schema](../../_shared/schemas/research-questions.schema.json)为准，包含 `goal` 和 `questions` 数组。每题包含 `id`、`topics`、`question`、`answer`、`status`、`evidence`、`unknowns`；完整回答放在 answer，不把正文缩写成摘要。

主题键为 scenario、mechanism、contribution、limitations、dependencies、cost、engineering、hypothesis、adoption；每题可绑定多个相关主题，装配器检查整体覆盖、重复 ID、空文本和未完成状态。它无法仅凭字段齐全证明问题足够具体或论证充分，仍须逐题语义验收。

当前 `assemble:insight` 是源码级装配器：evidence 的每项含 `kind`（author_claim／source_inspection）、`source_path`、`line_start`、`line_end`、`observation`。路径必须属于本项已固定并读取的材料，行号须有效；装配器从真实 Git blob 取出对应原文，生成固定提交链接，不接受编造的摘录。observation 说明材料与本题的关系，不能把源码解释标作运行结果。unknowns 的每项含 `issue`、`impact`、`next_step`，可选 kind 区分 research_gap（实际研究缺口，默认）和 scope_boundary（本轮明确不做的工作）。类别由研究者明确标记，不从关键词推断。answer、observation 和未知项正文不能引入一至三级或 Setext 标题；可用四级以下标题、段落和成对围栏代码块。

涉及外部反馈或真实执行证据的研究应使用数据契约允许的真实观察与手工研究报告，经父 Agent 核对后 stage；不能将这些材料伪装成源码证据塞入当前装配器。手工路径也必须交付同样完整的计划、逐题回答和覆盖关系。

## 先逐题验收，再综合

父 Agent 对照计划逐题核对回答、证据、未知项与状态；未交付的问题不得通过综合摘要补齐。partial／unknown 只有已明确回答边界、影响与补证动作，且不会使核心采用结论自相矛盾时才可接受；关键材料完全不可核查或不能形成自包含报告时登记受阻。回答充分性由人或执行AI逐题判断，不能只靠 Schema 或回答字数。

逐题交付完成后才写贡献、主要质疑、采用建议、创新假设和评分。贡献、主要质疑、创新假设与采用建议须用 `[Q01](#research-q01)` 形式回指具体问题（ID按实际问题替换），装配器检查至少有一个有效问题链接；检查跨题矛盾、反证和条件，严重限制必须影响采用建议；综合不替代或删除逐题回答。

最终 INSIGHT 保留综合阅读入口，并包含可导航的“研究问题与完整回答”正文，逐题展开完整回答、证据原文／位置；实际未解决项以“缺口”列出缺失、影响与下一步，无缺口不显示空栏目。status 仍保存在结构化输入及过程记录中，读者正文不单列“回答状态”。不能只给主题摘要或只链接本地问题文件，也不能默认折叠全部回答来保留一篇短评。长原文代码块按[输出标准](../../dsh-plugin-init/references/OUTPUT-STANDARD.md)折叠，来源链接与依据解释仍展开，完整原文保留在报告内。正式完整报告随快照的 reports 合并，源材料进入必要证据；本地 PLAN、逐题文件和 ANALYSIS 仅是过程副本，合并核对后当前研究不得依赖这些本地路径。

新流程不追溯伪造已有405项研究的逐题材料；旧报告继续兼容展示，不能声称它们已经满足逐题研究验收。重新生成页面只重排已有内容，不从摘要反向生成问题回答。尚未合并的旧 ANALYSIS 若继续使用新装配器，须实际补做逐题研究后提交新输入；不得机械填充问题来绕过校验，已完成记录不因此自动重写。

## Git 证据定位

逐题材料中的 `source_path` 必须来自本次固定提交的实际读取结果；装配器从研究上下文补入原始仓库 URL 和完整 commit，正式回答以文件路径及行号作为链接文字，链接目标绑定原始仓库与完整提交；不在链接后重复列仓库、提交、路径、行号或文件哈希。文件内容 SHA-256 继续保存在结构化源码证据中。结构化字段与历史兼容按[数据契约](../../_shared/references/DATA-CONTRACT.md#git-原始材料的可追溯定位)执行。引用必须说明材料支持的具体判断，不能只留下链接。非 Git 网页、API/npm 查询和执行结果仍须保存必要原始记录及采集或执行上下文。
