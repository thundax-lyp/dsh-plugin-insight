# 插件研究规范

## 核心目标与研究主线

将插件作为研究样本，借鉴论文审稿的方法识别核心贡献、检验关键主张，并通过比较和质疑推导新的技术或业务创新假设。
主线为“贡献识别 → 关键质疑 → 比较与解释 → 新创新假设 → 最小验证”。采用建议是研究的应用结果，不能替代贡献论证；工程核查、成本和兼容分析用于解释贡献成立的条件与落地边界。

- **贡献识别：** 区分作者声称的贡献与研究者识别的贡献，以宿主原生能力、同类方案、上游机制或既有业务流程为参照，说明具体增量和来源。技术贡献可以是机制、架构或有效组合；业务贡献可以是流程、分工、交付方式或成本结构的改变。未查到先例不等于首次创新，包装和集成也不自动等于没有贡献。
- **关键质疑：** 选择最影响核心贡献成立的一项或少数几项假设，给出最强支持、反例、其他解释和可推翻条件。一般工程问题只有影响贡献或验证时才展开，不以风险清单代替审稿式分析，也不为显得尖锐而强凑缺点。
- **新创新假设：** 从已核查机制、关键限制或跨插件比较中，尝试推广、组合、替换机制，或重新组织业务流程；明确从哪些发现推导、相对现有办法改变什么、为什么可能有效，以及最小验证和否定条件。组合设想需检查依赖、状态所有权、接口冲突和新增负担；业务设想分别判断需求、供给和商业意愿。

贡献判断、技术新意、业务增量、采用价值和证据强度分别表达。区分已有证据支持的贡献、有依据但待验证的创新假设，以及依据较弱的探索性设想；不得将后两者写成已证实创新或已确认市场机会。
不要求每篇必有创新：可明确“未识别出相对已有方案的贡献”“当前材料不足以判断”或“本次未形成新假设”，并说明依据或缺口。目录级材料只能支持候选主张与研究问题，不能包装成已完成的贡献核查。

## 来源、身份与分类

优先遵守用户指定来源。默认发现入口为：

- `awesome-dsh-plugin/awesome-dsh-plugin`：优先读取 `data/plugins` 结构化条目，而非生成的 README。
- `0xsline/awesome-deepseek-harness`：读取 README 和 CATALOG。

固定提交、文件路径、采集截止时间，记录分页、截断与访问失败。
分别报告目录条目数、去重组件数和仓库数；不能将发现的条目数写成当前可用插件数。

技术主类：agent-workflow（Agent 与工作流）、context-search（上下文与搜索）、
memory-knowledge（记忆与知识）、model-provider（模型与供应商）、tools-integration（工具集成）、
interface-input（界面与输入）、sessions-messages（会话与消息）、channels-remote（渠道与远程）、
runtime-deployment（运行与部署）、observability-cost（观测与成本）、security-governance（安全与治理）、other。

业务主类：software-delivery（软件交付）、research-knowledge（研究与知识）、
office-operations（办公与运营）、customer-service（客户服务）、content-creation（内容生产）、
personal-productivity（个人效率）、infrastructure（基础设施）、other。
按主要能力和用户流程分类，次要能力使用标签。不确定条目使用 other 并添加不确定性标签。

## 研究深度与证据边界

目录级研究覆盖身份、类型、描述、分类及出处；源码级研究检查入口、核心机制、宿主 API、
依赖、发布和兼容条件；本地测试必须记录真实执行；真实宿主验收必须绑定插件、宿主、模型及系统版本。
首次全量建档不要求安装执行全部候选。运行实验遵守用户授权范围，并隔离实验环境。

明确区分作者声明、源码核查、本地测试、真实宿主验收和独立反馈。
源码存在某机制不证明运行效果，模拟测试通过不证明宿主兼容。
不支持的主张保留未验证状态；已确认缺陷、设计限制、兼容风险和证据不足分别表达。

## 贡献成立条件与采用价值

先说明用户场景、原有办法和合格交付物，以这些条件检验贡献及新假设。按核心主张选择核查深度；涉及收益或采用判断时，分析依赖、流程、成本与结果。
源码、架构、测试和工程质量用于核实机制、解释收益及风险；不以代码审查报告或完整采用画像代替创新洞察。

| 维度 | 核心问题 | 判断依据 |
|---|---|---|
| 业务场景 | 谁在什么环境下，以什么频率完成什么任务？ | 用户角色、触发条件、输入、交付物、成功判据；区分作者设想与实际使用 |
| 问题与增量价值 | 原来如何完成，插件具体改变了什么？ | 对比宿主原生能力、同类插件、脚本及人工流程的耗时、错误、交接和结果质量 |
| 依赖与使用条件 | 要依赖什么才能启动并兑现能力？ | 安装依赖、效果依赖、必要与可选条件、权限及数据条件、依赖失效后的替代或降级 |
| 流程复杂度 | 安装到办结、失败到恢复需要付出哪些操作？ | 用户步骤、后台执行和失败处理三个层次中的配置、服务、交接、人工介入及恢复负担 |
| 总成本 | 一次合格任务和持续使用分别付出什么？ | 现金支出、人工时间、安装配置、复核、失败重试、运维及迁移成本，注明计量条件 |
| 结果与适用边界 | 收益是否兑现，哪些条件下不值得采用？ | 合格交付率、质量、端到端耗时、可靠性，以及规模、隐私、版本和资源边界 |

### 依赖分析

安装依赖决定能否启动，包括宿主／运行时版本、包、其他插件、模型接入、外部服务和账号权限。
效果依赖决定是否有用，包括模型能力、信息源可访问性、数据质量与规模、上下文／检索条件、
预算和人工判断。还应说明哪些能力依赖维护者持续适配或第三方服务持续提供。

为关键依赖记录用途、必要或可选、版本／权限／付费条件、失效影响、替代／降级方式及证据。
不把 package 依赖列表等同于完整使用条件；能安装、工具能注册、一次演示成功都不证明目标业务可办结。

### 流程复杂度分析

围绕同一任务梳理“准备与配置 → 输入 → 自动处理 → 人工确认／系统写回 → 验收”，同时检查失败恢复。
分别观察用户可见步骤、后台模型／工具／服务调用，以及异常后的重试、补偿、人工接管和重复操作风险。
记录服务与配置项数量、关键交接、人工介入位置及次数、需要的专业能力；不能只按界面点击次数判断。

“一句话完成”不代表总流程简单，后台复杂也可能合理地减少人工工作。比较采用前后的总负担，
判断复杂性被消除、由插件承担还是转移给用户，并说明这份复杂性换来了什么收益。

### 成本与收益比较

以同一类“合格任务”为计量单位，先定义验收标准和工作负载。现金支出与人工时间分别记录，
未说明人工单价时不能把小时与金额直接相加。区分首次部署／配置、日常使用和升级／迁移成本。

现金成本包括实际适用的模型／API、服务订阅、计算、存储和网络；任务成本包括失败尝试、重试、
人工复核与修正，不仅统计一次调用或成功样本的 token。固定费用须注明评估周期、任务量和分摊方法。
可计算“同批次总现金支出 ÷ 合格交付数”，同时报告合格率和人工时间；没有合格交付时不输出有限单位成本。
没有实测时使用有来源的估算，列明价格日期、币种、模型、调用量假设和遗漏项，不编造 ROI 或收益比例。

### 支撑性工程核查

按任务价值与风险选择源码核查范围：实现机制与上游归属、兼容与权限、数据流与外部副作用、
安装和卸载、异常恢复、测试及发布一致性。技术难度、创新与维护活跃度解释能力和长期采用风险，
不单独作为用户价值结论。采用建议说明适合谁、必要条件、收益代价和最小验证。

## 代码规模、能力清单与代码评价

代码行数复用 Node.js CLI [flosse/sloc](https://github.com/flosse/sloc)，锁定 npm 0.3.2；
项目 `plugin-inventory.mjs` 负责固定 Git 版本、限定组件、过滤文件、分组和 DSH 专有候选清单，不自写 LOC 算法。
比较过 node-sloc（CLI 输出选项较少）及 tally（本次查阅时尚未发布 npm、需源码构建）；选型看实际输出及接入负担，
不根据 Star 决定。sloc 0.3.2 CLI 的 alias 在本环境未生效，封装在临时目录将 md 映射为 html，仅取总行数；
将 cjs 映射为 js、mts／cts 映射为 ts，输出保留真实扩展名。不修改或执行目标代码。

- Markdown：只统计 `.md` 的文件数、总行数和字数；字数为每个 Han 字符计1，剩余连续字母／数字词计1，
  词内连字符／撇号可连接；标记和代码块内容不剥离。与 JS／TS 不合成总 LOC。
- JS／TS：`.js/.mjs/.cjs/.jsx/.ts/.mts/.cts/.tsx` 按扩展名分别统计文件数、总行数、代码／注释／空行。
  行数采用锁定版本 sloc 的口径，混合行可同时属于代码与注释，不强求相加等于总行数。
- 生产、测试和示例按路径分组；依赖、dist／build、vendor／third_party、声明文件和压缩 JS 默认排除并列出原因。
  人工核查启发式是否误排源文件、漏掉生成／复制／第三方代码；不能将净 LOC 当作原创量或人天。
- 只统计目标组件，必要共享代码另跑一次并单列，不能把整个 monorepo 当插件大小。Python和其他扩展名不纳入。
- 完整统计优先使用只读 Git 固定提交；抽读快照只能标“已核查文件子集”，不能输出全插件规模。

DSH 能力清单以[官方插件接口](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/basic/index.md)、
[Skill 注册](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/skills.md)与源码为依据：

| 项目 | 自动产物与人工确认 |
|---|---|
| 内嵌 Skill | 找 SKILL.md 入口并提取简单 name／description；区分示例、无效入口、第三方归属和真正注册的能力；外部 Skill 依赖另列 |
| Agent／Preset | AST 提取 agentPresets.register 的静态 id 候选；角色提示词、运行实例和 AGENTS.md 不计为定义；配置里的预设与动态工厂人工核查 |
| 工具、用户命令 | 提取字面量名称及路径／行号，名称去重，命令别名单列；定义、注册与运行时可用性分别判断 |
| 后台与界面 | 列事件、定时器及已识别 UI 注册候选；自动注入、任务调度和其他适配接口需人工补全，不以调用次数代替能力数 |
| 使用负担 | 从清单和接线核查必要服务、外部账号／密钥、必填配置；记录持久化目录、跨项目状态、联网和子进程副作用，不保存密钥值 |

脚本使用 TypeScript AST，避开注释和字符串示例；字面量名去重只是静态候选数量，confirmed_count 默认 null。
动态参数、工厂和解析错误保留路径／行号；未检出不等于确认没有。YAML／JSON 组合、作用域覆盖、别名、
动态提供者及真正挂载情况需要人工检查；同名跨作用域可能表示不同定义，不能将去重数当运行总数。

详情在统计之外还须给出：

- **代码评价：** 用具体实现说明职责划分、宿主耦合、错误处理、状态与恢复、测试有效性及维护成本，
  区分确认缺陷、设计取舍和未验证风险；每个重要判断链接固定版本源码，解释对使用的影响。
- **可借鉴处：** 指出机制／模块解决什么问题，为什么值得复用，依赖条件、移植／维护代价与验证方式；
  普通但有效的集成同样可以值得借鉴。没有足够依据时说明未发现可推荐复用的设计，不凑数。

代码统计和能力数量只是分析材料，不作为不透明评分、质量保证或业务收益证明。

## 从事实到洞察

洞察应识别和检验贡献，形成值得继续研究的技术／业务问题及创新假设，并说明对研究、开发或采用的影响。
数据采集、分类、数量变化和功能介绍是研究基础，不能单独作为采用建议或生态结论。
每个研究问题按三个层次推进，并明确区分证据与推断：

| 层次 | 问题 | 证据要求 |
|---|---|---|
| 事实 | 什么发生了变化，在哪个版本、任务或人群中发生？ | 引用固定版本的来源、实现、执行记录或反馈，注明范围 |
| 解释 | 变化可能解决什么问题，机制如何起作用？ | 建立事实与机制的联系，同时检查反例和其他解释，不凭提交说明推断作者动机 |
| 推演与决策 | 由贡献和质疑可推导什么新假设，对研究、开发或采用有什么影响？ | 明确推导依据、相对增量、适用条件、收益代价及可执行的证伪验证 |

不能从“新增某机制”直接推出“效果提高”，也不能从多个项目同时更新直接推出因果或生态趋势。
证据不足时产出有依据的待验证假设或待核查问题，允许明确说明本次未形成新洞察。
洞察的输出结构由[输出标准](../../dsh-plugin-init/references/OUTPUT-STANDARD.md)统一维护。

### 围绕核心贡献形成关键质疑

重点点评选择最影响贡献成立的一项主张，沿“贡献主张 → 实际支持 → 关键缺口 → 对贡献的影响 → 可探索的新方向”追问，
不为显得尖锐而堆砌缺点。质疑对象是能力主张、实现和使用条件，不猜测作者动机或评价人格。

- **收益归因：** 提升来自插件机制，还是更强模型、更多调用、更多人工或更宽松的验收？
  尽量用同任务、同资源的简单方案作对照；不能控制的差异明确保留，不能把总预算增加当作机制胜出。
- **负担去向：** 自动化减少了哪一步，又把拆任务、维护环境、复核和兜底交给谁？
  区分局部操作变快与端到端办结；同时观察速度、合格率和人工投入，避免单项指标掩盖退步。
- **承诺范围：** 演示、正常路径、局部检查分别证明到哪里？检查是否真正约束最终交付，
  失败后谁负责恢复？不能把“提供评审／恢复功能”直接当成严格放行／自动恢复保证。
- **复杂性必要性：** 宿主原生能力、简单脚本或人工流程能否以更低总负担交付同样结果？
  包装和集成本身也可能有价值；新意、采用价值及证据强度分别判断，不因技术普通就否定业务收益。

每条重点点评优先指出最有力的支持，再落到一个会改变贡献判断的限制；优点缺点不要求数量对称。
证据不足只能收窄结论，不能直接判为无效；局部缺陷也不能泛化为全部能力不可用。
在限制之后说明仍值得借鉴的机制、适用人群或可执行验证；若没有足够价值依据，可以明确暂缓采用。
避免以“仍需验证”收尾，写明验证哪项主张、采用什么对照、观察什么，以及什么结果会改变建议。

此方法借鉴 `arxiv-paper-wechat` 的编辑与发布规范，以及 2026-10-16、2026-10-19 成稿中
“编辑点评／为什么值得读”的论证方式，适配为插件贡献检验与创新推演。共享规则在本仓库维护，
执行不依赖邻仓路径；论文评分、精选门槛与阅读星标不迁入插件评价。

### 围绕问题进行同条件比较

先确定贡献相关的共同问题、目标用户、具体失败或瓶颈及成功判据，再选候选插件；不以逐个介绍功能代替比较。
例如记忆方案可围绕纠错、跨项目隔离及最终任务质量比较，多 Agent 方案可围绕中断恢复和重复执行比较。
主题按用户范围和实际价值选择，不要求每次覆盖所有类别或执行全量深评。

比较记录共同业务任务、合格交付标准、输入、插件／宿主版本、模型、环境、依赖、流程及预算；无法对齐的条件单独注明。
同时考虑直接竞品、DSH 原生能力、简单脚本及人工流程，检查正确性、成本、可靠性、使用负担和迁移代价。
区分能力差异、实现差异和用户收益；复杂机制的必要性可用最小替代方案或针对性实验检验。
比较应解释不同机制和业务安排的关键取舍，检查贡献归属和已有先例，再判断能否推导新假设。没有运行证据时可比较实现与声明，但不把它们写成已验证的效果排名。

### 核查当前能力与问题

围绕固定版本的实现、缺陷记录、发布说明和使用反馈核查当前能力，不要求开展插件版本差异或演进研究。
核对同类方案是否在解决相同问题，DSH 原生能力是否影响插件的独立价值；材料冲突时直接说明当前判断的依据和边界。
生态趋势须说明样本选择、观察窗口及其他解释；单插件变化只支持相应范围内的判断。
没有代码更新也可能因新反馈、新竞品或原生能力变化而需要复核，不能只用代码指纹决定研究是否过期。

### 从供给缺口到机会验证

某类条目少或不存在，只能说明当前来源中的供给情况。提出“值得做”的机会时，检查：

- 是否有具体用户反复遇到同类问题，场景、频率、严重程度及受影响人群是什么。
- 现有替代方案的实际代价在哪里，用户如何绕过问题，是否有真实使用或解决尝试。
- Issue、使用反馈、修复记录和实际任务是否相互支持，反馈是否独立、是否可能重复或偏样本。
- 最小方案如何改善可观察结果，其成功判据、成本边界和可能推翻机会判断的证据是什么。

把需求证据、供给证据和商业意愿分别判断；抱怨不等于愿意迁移或付费。
缺少需求或结果验证时称为机会假设，列出缺失证据和最小验证，不升级为已确认市场机会。

## 工程更新分析

近 7／30／90 天活跃度必须有明确截止时间和足够完整的历史。
区分功能、修复、兼容、重构、文档、依赖及机器人更新。
更新面积同时描述代码面积（模块与有效增删）、功能面积（用户流程、平台、集成）、
风险面积（接口、权限、持久化、迁移及外部副作用）。文件数不能单独表示影响。

区分原始开发、集成适配、验证和长期维护工作。
有效工程量排除第三方内置代码、生成代码及复制代码，不从行数推算人天。
Stars、forks、下载和供给量不等于活跃用户、可靠性或需求；目录停更不证明生态降温。

## 内部增量复核

每轮先核对当前快照中已有研究成果的变化；未变且依赖仍有效的成果保留，不占本轮研究额度。按数据契约优先选择需更新的已有项，再用尚未研究的新项补足额度；对所选项按贡献、质疑与新假设主线重新分析，并复核相关成立条件。依赖指纹变化时标记 `needs_review`，即使代码未变也进入待复核范围，并复核关联比较和生态缺口。
目录覆盖变化也会影响生态判断，即使原有插件代码没有变化。
当前快照引用的测试必须标明适用版本，不能把旧版本通过转写为新版本通过。需要追溯时查 Git；不要求保留每轮本地会话或测试副本。
内部复核核对旧结论与当前证据是否匹配，记录修订依据以维护当前快照；INSIGHT 只表达当前贡献、关键质疑、创新假设及适用条件，不展示旧稿差异或版本演进。
重点复核业务场景、安装／效果依赖、流程负担、单位合格任务成本和收益边界是否变化。
外部模型／服务的价格、权限或可用性变化也可能影响采用价值，即使插件代码未变化。
跨插件、原生能力或外部反馈引起的影响需主动复核；现有自动依赖失效只覆盖已登记的插件与指纹。
在现有 findings 字段内记录结论、判断性质、证据和依赖；完整洞察及跨主题论证放在研究报告中。
不要为本文新增未定义的 Schema 字段，也不要把待验证假设等同于依赖变化后的 `needs_review`。

报告结构、每轮统计及交付校验统一遵循[输出标准](../../dsh-plugin-init/references/OUTPUT-STANDARD.md)。
本工程更新本地研究结果，不自动发布推荐或修改第三方仓库。
