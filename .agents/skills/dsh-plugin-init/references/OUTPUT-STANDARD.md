# 研究输出标准

本标准适用于首轮研究、后续整轮研究、同轮断点恢复与独立单插件洞察。
列表编排 Skill 负责队列与发布，单插件洞察 Skill 负责证据、详情和观察批次；独立调用洞察不要求生成全轮入口。
共同输出要求只在本文件维护；Skill 保留流程、触发条件和自身特有约束。
字段与引用规则以[数据契约](../../_shared/references/DATA-CONTRACT.md)及 JSON Schema 为准，
研究判断遵循[研究规范](../../dsh-plugin-insight/references/RESEARCH-STANDARD.md)。

## 当前快照与实现边界

研究事实的唯一正式真相是当前档案及其引用的当前分析、来源和必要证据；本轮记录先在 runs 暂存，校验后最终合并。完整语义见[数据契约](../../_shared/references/DATA-CONTRACT.md#唯一当前快照与本轮增量)。
展示输入只组织当前成果，生成页面不承担人工研究真相。下一轮、当前校验和页面生成不应依赖旧 SESSION、历史 manifest 链或已经合并的 runs。

正式快照为 `data/catalog/SNAPSHOT.json`；WORK 暂存与单文件原子合并已由 snapshot-data.mjs 实现。分析原文、展示数据和必要证据内容保存在正式快照内；文件式档案、META 和页面是可重新生成的兼容输出。迁移缺失原件有显式限制，不当作新验证。

## README 生成物与读者路由

项目根 `README.md` 是面向读者的研究成果总入口，由 `npm run render:research` 生成，不手工维护。
生成输入为 `data/catalog/PUBLICATION.json`，结构由[发布输入 Schema](../../_shared/schemas/publication.schema.json)约束。
README 由独立块函数合成：本周新增 → 最新 → 最热 → 推荐 → 分类导航与每类热门插件 → 研究出处 → LICENSE → 更新时间。
LICENSE 区块链接根 `LICENSE`，标明 CC0-1.0，位于末尾更新时间之前。
Markdown 版式由 `.agents/skills/dsh-plugin-init/assets/templates/publication/` 维护：README／CATALOG 为总模板，UPDATED／WEEKLY-NEW／LATEST／HOT／RECOMMENDED／CATEGORIES／SOURCES 为块模板，
条目、分类、插件详情入口、META及徽章使用对应小模板。`.agents/skills/dsh-plugin-init/scripts/publication/blocks.mjs` 只负责筛选、排序与装配，不硬编码标题及段落版式。
总入口读取模板并填充已核验数据，同一列表不维护两份 Markdown。
不展示研究历史、本轮范围、完成计数、研究深度、工程使用、内部数据入口或“具体来源版本与覆盖限制见本轮报告”等过程说明。

- **更新时间：** 取当前 META 快照最新北京时间日期；无 META 时用会话检查日期。独立的 META 时间保存在数据中。
- **本周新增：** 使用已核实 npm 包在官方注册表 time.created 的首次发布时间，筛选北京时间本周一至更新时间内首次发布且已完成分析的插件，链接稳定详情并附用途。已有包本周发新版、本工程首次入档和仓库创建都不算新增。缺少包名、发布时间或采集失败时不纳入；没有符合条件的条目时隐藏整个“本周新增”区块，包括标题，不显示占位文案。
- **最新：** 按已确认的仓库 `pushed_at` 时间降序，最多3项；缺失时间不参与，默认不是插件创建时间或新发布排名。不展示仓库更新时间徽章或相对时间。
- **最热：** 按 GitHub Star 降序，最多3项，同分用稳定身份排序；缺失数量不填0或参与排名，热度不等于质量。
- **最新／最热条目：** 插件名后附功能短述，直接复用与详情同一固定版本的 `summaries.text`；最热再展示 Star 徽章，最新不展示时间徽章。不另维护简介或机械截断。
- **推荐：** 人工选择值得安装或条件试用的候选；在候选集合内，使用当前档案有效的技术创新、业务创新百分制均分降序排列，同分按稳定ID升序。无评分、任一轴未知、版本不匹配或待复核项排在已评分项之后，并按稳定ID排序；不能把缺失评分当0。observe项不进入推荐，不因高分自动入选。
  分数、分项、综合排序值、评分理由及“待评分”等评分状态均不展示在README、分类页或INSIGHT中，读者只看到推荐顺序；具体数据只存JSON。评分标准见洞察Skill研究规范。保留推荐理由、质疑及条件。
  没有验收证据仍不得标“值得装”，脚本变化提示待复核。推荐与最新／最热分开，不能用热度自动推出采用价值。
- **分类导航与列表：** 在 README 内先提供分类导航，随后每类按 Star 降序展示最多 5 个已完成插件的
  META 和“用途／亮点”两项短评，不展示“思考／建议”；分类标题链接对应完整分类页，每类末尾保留“更多”入口。插件标题直接链接详细分析，不再单列“详细分析”行；完整分类页保留四标签短评，按插件名字母顺序排列，页首先提供“插件／主要用途／关键使用条件”比较表。表内插件名跳转本页短评，主要用途复用同版本功能摘要，关键使用条件复用同版本使用建议（优先发布输入 advice，否则沿用原稿“建议”），不机械截断或推断条件；单元格转义竖线与 HTML 特殊字符。首页与分类页分别标明排序依据。
  首页“用途”沿用研究短评，“亮点”直接复用同一固定版本的 `summaries.text`，用日常语言说明提供的能力与特点，不复制源码路径、事件名或接线细节；技术短评仍保留在分类页与详情中，不把功能说明改写为效果保证。
- **研究出处：** 两个 GitHub 发现目录放在 README 最后；固定提交、证据边界和必要依据保存在当前快照；本轮错误与断点在合并前保存在 runs。

固定出处：

- [awesome-dsh-plugin/awesome-dsh-plugin](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin)
- [0xsline/awesome-deepseek-harness](https://github.com/0xsline/awesome-deepseek-harness)

子页面职责：推荐页展开人群、采用理由、思考、条件与试用方法；分类索引页链接各分类，完整分类页按插件名字母顺序呈现短评；
单插件详情承担完整采用分析和证据引用；Git 内运行清单说明来源版本、范围、状态、摘要与复现命令。
本轮原始采集、观察、断点和报告先暂存在 `data/runs/`；支撑当前结论的分析和证据在最终合并时落入正式快照，其他过程副本不要求永久保留。
工程执行另从根 AGENTS 路由到规范、Skill 和脚本，不进入生成的读者导航。

生成器核对运行清单、当前档案、详情摘要、四标签唯一性、推荐对象和页面存在性；分类数量由当前档案与发布输入计算，
不手填。只有 complete 项可进入点评与推荐，阶段发布同时说明未完成数量。
推荐为 install 时须有固定版本的真实宿主验收证据；这只是机械必要条件，收益和环境适用性仍须人工审阅。
生成器不分析插件、不发明推荐、不把代码测试通过写成目标插件效果通过。

发布顺序：生成本轮观察与详细分析 → 在本轮暂存区校验并形成候选 → 归纳展示输入 → 复核基线与全部依赖 → 最终合并当前快照 → 生成并回读页面。
未选、受阻和未完成项保留有效的当前成果；只有经过核实的失效状态才调整当前结论和推荐。当前页面的完整条目集从当前快照取得，不靠历史 manifest 补齐。
当前快照应能独立重新生成 README、分类和详情展示页；人工分析原文是当前快照引用的正式材料，不留在可清理 runs 中充当唯一依据。

正式更新使用 `snapshot stage／plan／apply`；旧 publication-data.mjs 仅保留兼容实现，并拒绝单独覆盖正式派生发布输入。发布 records 绑定当前 catalog 分析摘要，未选、失败和受阻项保留当前有效记录；受依赖变化影响的失效结论退出推荐与当前展示。
不得用临时脚本直接覆盖正式数据来替代事务合并，也不得手写 README 或从静态候选自动生成推荐判断。

## 文件位置与命名

| 产物 | 位置 | 要求 |
|---|---|---|
| 研究入口 | 根 `README.md` | 由模板生成，插件标题链接稳定详情入口 |
| 唯一正式快照 | `data/catalog/SNAPSHOT.json` | 当前档案、来源、分析原文、证据内容及展示输入；原子合并点 |
| 本轮工作记录 | `data/runs/<round>/WORK.json` | v2保存固定基线与过程文件摘要索引；合并后可按引用清理 |
| 档案兼容输出 | `data/catalog/PLUGINS.json` | 从正式快照生成，不单独人工维护 |
| 发布兼容输出 | `data/catalog/PUBLICATION.json` | 从快照生成，records 保存当前有效完成记录，不引用历史会话 |
| 插件路径注册表 | `data/catalog/PLUGIN-PATHS.json` | 稳定 ID 到可读插件目录的唯一映射 |
| 当前详情展示 | `data/plugins/<plugin-slug>/INSIGHT.md` | 从快照 reports 原文生成，包含最新 Issue 信息 |
| 当前 META | `data/plugins/<plugin-slug>/META.json` | 当前采集结果；本轮采集先暂存，核实后更新 |
| 旧运行清单 | `data/manifests/<round>.json` | 新文件由 .gitignore 忽略；已跟踪且仍被当前工具或详情引用的文件暂留，解除依赖后删除 |
| 本地来源输入与问题 | `data/runs/<round>/INPUT.json`、`INPUT-PROBLEMS.json` | Git 忽略；固定目录解析、身份核实结果与未解决边界 |
| 本地会话与进度 | `data/runs/<round>/SESSION.json` | Git 忽略；v2为指向同轮WORK的兼容入口；实际会话头、状态和检查点独立存储 |
| 本地单插件观察 | `data/runs/<round>/observations/<plugin-slug>.json` | Git 忽略；批次只含本项，历史多项批次可用 MULTI-PLUGIN.json |
| 拆分过程依赖 | `data/runs/<round>/process/{queues,sessions,records}/<sha256>.json` | WORK 引用的不可变队列、会话状态和单项记录；INPUT 保留完整固定清单 |
| 过程迁移审计 | `data/runs/<round>/WORK-MIGRATION.json`、`migration-originals/work-storage-v1/` | 迁移摘要与旧 WORK／SESSION 原始字节，不由 clean 自动删除 |
| 本地研究原稿 | `data/runs/<round>/insights/<plugin-slug>.md` | Git 忽略；本轮暂存原稿，合并时将当前原文落入正式位置 |
| 本地材料索引 | `data/runs/<round>/snapshots/<plugin-slug>/MATERIALS.json` | Git 忽略；机械绑定 checkout、作者材料、inventory 与待核查候选，不承载结论 |
| 本地发布输入 | `data/runs/<round>/PUBLICATION-INPUT.json` | Git 忽略；人工审阅的推荐、摘要、能力、META 映射与建议，供发布 plan／apply 使用 |
| 本地报告与推荐 | `data/runs/<round>/REPORT.md`、`RECOMMENDATIONS.md` | Git 忽略；描述范围、依据、判断及未完成项 |
| 本地原始材料 | `data/runs/<round>/snapshots/` | Git 忽略；保存来源、源码、版本、统计、META及失败材料 |
| 分类索引与完整页 | `data/views/categories/INDEX.md`、`<CATEGORY>.md` | 当前分类页按名称排序，与 README 一起生成 |
| 迁移审计 | `data/catalog/MIGRATION.json` | 既有路径迁移审计；原件位置可指向本地运行目录 |
| 临时计划／缓存／源码检出 | 系统临时目录或 `data/tmp/`、`cache/`、`checkouts/` | 可重建且不提交，不放正式证据 |

`plugin-slug` 首次由 owner、repo 组成 `owner--repo`，子组件追加稳定组件名；统一小写。
首次分配写入注册表，仓库改名或组件移动后保持目录不变，不根据新名字再次创建目录。
`round` 使用北京时间日期与当日序号 `YYYY-MM-DD-NN`（至少两位，从01起），如 `2026-10-19-03`；新轮次使用未占用目录，不能复用历史编号。日期是轮次开始日，续跑跨日不改名。SESSION、REPORT、RECOMMENDATIONS 及 SOURCE、META 等文件不再重复添加时间；精确时间保留在 JSON 字段中。独立 META 采集批次可在 snapshots 下使用独立批次目录，避免覆盖已有证据。
观察 `run_id` 使用轮次与插件标识形成唯一 ID；历史内部 ID、提交 SHA 与精确 ISO 时间保留在字段中，不为改目录而改身份。

来源采集、执行记录均须保留实际版本、环境与结果边界，不保存凭据，不把作者日志写成本地执行。
完整源码文本与抽读范围分别标识；输入示例在 init 的 assets 内，不导入真实档案。
历史版本需要时从 Git 查阅，不要求永久保存每轮本地原稿或迁移原件。更新规范不自动删除既有文件。
`.gitignore` 排除本轮过程、缓存、checkout 和锁／临时文件；当前快照及其仍引用的分析、证据不能被忽略为可丢弃过程。

## 本地 runs 与 Git 清单

- runs 是本轮工作区，不是历史真相库。只在尚未合并、失败待查或需要同轮恢复时保留相关材料。
- 最终合并前，将当前快照仍需引用的分析、证据和 META 落入正式位置并校验，不能留下指向待清理 runs 的有效引用。
- 合并结果回读、当前引用完整且可独立生成页面后，本轮无引用副本可以清理；永久归档不是交付条件。活动锁、未合并记录和未知文件不能当作已合并副本清理。
- Git 跟踪正式当前状态的变迁；不生成逐插件历史导航。历史 manifest 仅供首次迁移和可选追溯，不成为当前生成或新研究前置条件。
- `.gitignore` 忽略新增的 `data/manifests/` 过程文件；已跟踪文件不会因此退出 Git。清理旧文件须核对引用并通过后续提交删除，不使用强制添加继续累积历史 manifest。每日 META 更新只暂存当前数据和页面，不暂存该目录。
- 现有 `maintain:runs` 只清理它支持的旧重复视图，不能充当新模型的合并后清理器。新清理流程须先预览引用与合并状态，再执行并回读；本次不执行清理。

## 研究清单与断点

新轮次从当前快照读取基线，固定来源版本与本轮选择，不需要上轮会话。基线不足以支持的变化判断标 unknown，身份失败和范围差异明确记录。
新过程将完整清单、队列变化、会话状态和逐项记录分开，具体职责与原子更新遵循数据契约；旧原件经显式迁移后保留。
本轮 SESSION 与检查点用于恢复尚未合并的工作；记录完整不代表已写入正式快照。丢失旧轮次材料不影响下一轮，丢失本轮未合并材料则重新采集受影响项，不伪造完成态。
新轮次先核对全部已有研究成果；确认未变的保留原成果、不占额度，再按数据契约优先选择更新项并用新项补足。只有所选项完整分析，旧结论不直接充作本轮完成记录。
报告区分清单总数、已有成果核对数、确认未变数、待更新数、所选更新／新研究数、记录完成数、合并数、受阻及未选数；核对未变不计为新完成，不能从 next 为空推断全部合并成功。

## 先分析，再归纳与推荐

研究生成顺序为“单插件详细分析 → 分类列表 → 推荐页”。先完成贡献识别、关键质疑、新创新假设及其证据论证，
再提炼短评与推荐，不能先定榜单再寻找支持材料。读者可从 README 的推荐页或分类列表进入详情。

- **单插件详细分析：** 放在本次研究报告的独立小节，提供稳定锚点；覆盖场景与原有办法、
  核心贡献、关键质疑、新创新假设及最小验证；依赖、使用及失败恢复流程、成本与效果用于解释成立条件，另保留证据边界和有依据的采用建议。规模扩大确需拆分时，
  本轮使用 `data/runs/<round>/insights/<plugin-slug>.md` 暂存；最终合并时保存当前正式分析及必要证据，详情展示页从它们生成。
- **分类列表：** 以业务场景为主分类，技术类别作为辅助信息。每个插件使用下述四标签短评，
  标题链接到对应详细分析；标明范围、截止时间和研究深度，未深评条目明确哪些内容仍未知。
- **推荐页：** 最后从已完成详情中筛选，链接对应分析。说明推荐给谁、为什么、思考、
  必要依赖与成本、证据层级及最小试用方法；未形成推荐时直接说明原因，不凑数。

推荐页区分两个用途：

- **什么值得装：** 面向持续采用，必须有目标版本的实际安装与真实宿主验收证据，
  并明确用户场景、收益依据、持续负担和兼容范围；证据缺失或过期时保留待验证状态。
- **本周最值得试：** 面向小范围探索，说明本周哪项新发现或变化值得验证、适合谁、
  试什么以及成功／停止判据。源码级证据可支撑试用候选，不能据此写成已验证增效；
  明确本周起止日期与候选覆盖范围，不把有限样本写成全生态最佳，也不隐含定期执行授权。

每轮重新完成全部所选条目的详情，再生成分类短评和推荐；与当前快照对照，需要更早版本时查 Git，不要求保存每轮报告。
同轮续跑复用已完成项，README 指向实际生成的最新产物。
不为输出格式重新初始化数据或增加未定义字段；创新评分使用数据契约定义的innovation_scores。

## 报告共同结构

读者版单插件 INSIGHT 的“研究范围”和“结论状态”分开呈现。研究范围只列仓库地址、版本号和版本日期，可附固定提交链接；版本日期注明是发布日还是固定提交日，不能用研究或采集时间代替，无法核实时写未知。
读者INSIGHT不单设“分发、维护与独立证据”或“分发与兼容”章节，不重复安装渠道、包元数据、Star、Issue等信息；这些保存在JSON及已有badge中。直接影响贡献判断的独立证据放回对应论证，影响建议的分发或兼容限制在该建议或依赖条件旁简述。证据不足在结论状态或验证边界中说明，不逐项回顾检索过程。
INSIGHT 只展示所研究版本的当前状态、贡献、质疑与创新推演，不设置版本差异、历史对照或与旧 INSIGHT 的差异章节，也不以“维持／修正／新增”回顾研究过程。内部增量核对用于保证当前结论有效，不构成插件版本演进研究。
研究时间、运行 ID、稳定身份和采集截止时间保存在证据、观察批次及会话元数据中，不要求出现在读者正文；实际核查范围和未执行项放入“验证与边界”。结论状态分别说明已有贡献、待验证设计假设及探索性设想。

整轮过程报告至少覆盖以下内容；允许根据规模合并小节，但不能遗漏事实边界。单插件读者正文按上述展示要求组织，不照搬过程信息。

1. **范围与截止时间：** 本次模式、运行 ID、来源、目标插件、采集截止时间及排除范围。
2. **来源覆盖：** 成功与失败来源、固定版本、分页／截断／权限限制，以及是否足以支持总体统计。
3. **结果统计：** 按下述模式说明条目、组件、仓库及变化情况，写清统计口径。
4. **研究结果与变化：** 围绕贡献、质疑和新假设，区分事实、解释、推演与决策影响，按下述洞察结构说明关键判断及证据；记录代码／功能／风险面积，无实质变化时直接说明。
5. **结论状态：** 本次新增、修订、仍有效及待复核结论，包含受影响的同类比较和生态缺口判断。
6. **验证与边界：** 区分作者报告、源码核查、本地测试、真实宿主验收和独立反馈；记录实际结果及未覆盖项。
7. **未完成项：** 采集错误、待核查问题、下一步最有价值的验证及采用条件。

没有相关内容的部分注明“不适用”及原因；验证未执行写“未执行”，不能写成通过或失败。
报告中的数量、版本、结论状态必须与观察批次和应用后档案一致。大规模明细保留在结构化数据中，
报告概括关键变化并引用具体条目及证据，不复制全部原始数据。

## 贡献的场景与成立条件

重点点评及专题比较先交代研究问题、业务场景和原有办法，再围绕核心贡献选择条件分析的深度。
贡献识别、质疑和推演的方法以[研究规范](../../dsh-plugin-insight/references/RESEARCH-STANDARD.md#核心目标与研究主线)为准；下述画像用于支撑贡献与采用判断，不替代主线，也不要求无关条件展开成空模板。
目录级条目未完成核查的维度标明未知或作者声明，不要求为全部条目虚构完整测评。

涉及采用价值或收益主张时，重点插件的报告至少能回答：

- **场景与问题：** 用户、任务频率、输入、合格交付物和原有替代办法，具体改善哪一步。
- **依赖：** 安装依赖与效果依赖分别列出；关键项说明用途、必要／可选、版本／权限／付费条件、失效影响和替代方式。
- **流程：** 简述准备、处理、人工确认／写回、验收及失败恢复；区分用户操作、后台执行和异常处理负担。
- **成本：** 分列首次配置、持续使用及迁移成本，注明现金和人工时间、实际／估算、计价日期及工作负载。
  按合格任务计量时同时给出验收标准、合格数、总尝试数和失败／重试／复核是否计入；没有合格结果不输出有限单位成本。
- **结果与选择：** 相对基线的质量、端到端耗时、可靠性和总负担，适合／不适合的人群及成立条件。

缺少数据时说明缺口和下一步验证；不同模型、任务量、免费额度或人工投入下的成本不能不加说明地直接排名。
证据和分析记录到现有 findings 与报告中，不为画像添加未定义的 Schema 字段。

## 洞察表达与专题比较

每篇 INSIGHT 的核心分析依次覆盖以下内容，可合并小节，但贡献、质疑和新假设须能被读者直接定位：

- **核心贡献：** 作者主张、研究者判断、已有参照及具体技术／业务增量；给出支持证据、归属和判断范围。
- **关键质疑：** 最影响贡献成立的假设、最强支持、反例或其他解释，以及质疑对贡献的影响。
- **新创新假设与验证：** 区分已有贡献、有依据的待验证假设及探索性设想；写明推导依据、相对改变、成立条件、最小实验、观察指标和否定条件。未形成贡献判断或新假设时明确原因，不凑数量。

创新推演是正文重点，保留独立且醒目的章节；有多个方向时先概括各自增量、关联和验证优先级，再展开推导与实验。首屏短评或结论摘要提示最有价值的方向，并链接实际存在的章节；突出重要性不等于提高证据等级，不设数量或篇幅配额，不强凑假设。

上述判断及采用、迁移、技术路线或生态机会结论共用以下证据链，不另建重复论证：

| 内容 | 必须回答的问题 |
|---|---|
| 判断 | 一句话说明发现及其状态：证据支持的判断，还是待验证假设；限定研究问题和样本 |
| 支持证据 | 哪些版本、实现、任务结果或独立反馈支持它，分别证明到哪一步 |
| 反例或其他解释 | 什么观察与判断不符，是否存在采样、环境、成本或替代机制的解释 |
| 适用条件 | 哪些用户、任务、宿主／模型版本及环境下可能成立，哪些范围未覆盖 |
| 推演与影响 | 能推导什么新假设，推导依据是什么，对研究、开发或采用有什么改变，收益与代价是什么 |
| 下一步验证 | 最小可执行实验或补证动作、观察指标、成功判据，以及什么结果会削弱或推翻判断 |

正文围绕“相对什么已有办法提出什么贡献、为何可能成立、关键质疑是什么、由此产生什么新假设及如何验证”展开，
按“事实 → 解释 → 推演与决策”呈现证据链；采用建议作为应用结果，不以功能清单、增长数字或通用风险提示代替论证。
缺乏运行验证时明确标记机制推断或待验证，不把未验证效果写成排名或收益结论。
不为满足报告结构强行生成洞察；无新判断时说明检查结果、证据缺口及最有价值的下一步。

专题比较围绕共同问题组织，记录候选及选择理由、基线、版本／环境／预算、成功判据、
贡献归属、机制／业务取舍、可推导的新假设、已验证和未验证的表现、成本及迁移代价。不能对齐的条件单独列明，避免配置不同的结果直接排名。
专题内容放在本次研究报告中；README 链接实际存在的专题报告，并用有条件的摘要说明主要判断。
不要为未完成专题创建结果链接，也不复制完整论证到 README。

生态机会须分别交代供给覆盖、用户问题证据、替代方案代价、真实解决尝试和最小方案验证。
只有目录数量或未发现竞品时，明确限制为供给观察，不能命名为已确认需求或市场机会。
现有结构化 findings 保存判断性质、文本、证据与依赖；上述论证通过报告表达，不要求增加 Schema 字段。 创新评分及其计算依据另存档案innovation_scores，不把评分理由作为报告必填段落。

## 面向读者的洞察短评

分类列表中的每个插件采用以下四个固定标签，每项用一句或必要的几句短述，方便扫读。
单插件详情的洞察短评也按此结构归纳；不把全部内容挤成一句话，不机械限制字数。

- **用途：** 用“受众／场景 + 核心能力”直接说明插件为谁做什么，例如“面向需要定期汇报工作的个人或团队，从实际活动记录生成报告，并支持回查来源”。按证据限定能力，不以“用户希望／需要……”的需求描述代替插件能力。
- **亮点：** 相对已有参照最值得关注的技术或业务贡献；无足够依据时明确为候选贡献，注明作者声称、机制推断或实际验证。
- **思考：** 最影响核心贡献成立的质疑及其后果，围绕归因、必要性、前提或证据缺口。
  已确认的限制直接陈述，不包装成悬而未决的问题；尚无答案的质疑写清缺口，不能暗示已证实无效。
- **建议：** 优先研究或验证什么新假设，说明推导依据与关键判据；未形成新假设时给出最有价值的补证动作。有采用依据时再说明适合谁及安装／试用／观察条件，不强行生成推荐。

短评由详情归纳，必须保留会改变选择的条件；每项突出重点，不重复完整论证。
每轮按当前证据形成点评；一致或改变的依据保存在内部复核记录，读者短评直接表达当前判断。

- 使用具体任务、机制与后果，例如把“流程复杂”改成“首次要维护本地 OCR 环境，偶发收票者可能难以摊薄配置时间”。
- 把“快／便宜／自动化”的主张与合格率、全部预算及人工责任连起来；没有实测时使用条件判断。
- 将采用优先级、技术新意和证据强度分开表达；不得用推荐程度暗示已完成宿主验收。
- 保留会改变选择的证据和边界，避免宣传式总结、人格嘲讽、无依据的失败断言，以及每个插件都能套用的泛泛警句。

洞察短评由现有分析归纳，不充当新的证据。它与完整洞察共用证据链，
记录在报告及分类列表中，不增加 Schema 字段；README 只保留有条件的摘要并链接相应产物。

## 内部增量统计与复核

首轮说明候选、去重组件和仓库数、条目类型、分类分布、研究深度及未核查范围。
后续轮次在内部记录来源与插件变更统计，核对旧结论是否仍适用；读者 INSIGHT 只呈现当前判断，不输出版本差异或旧稿对照。
无变化不免除分析；没有新洞察如实记录，不为制造差异改写观点。失败与受阻不导致删档。
统计应与脚本会话、观察批次及应用后的档案一致，不能把目录供给量写成可用插件数、用户量或需求规模。

## 交付验收

应用计划前检查候选档案和语义变化；基础档案变化时重新生成计划。
交付前先校验本轮记录和候选快照，再完成最终合并与生成检查。新模型的验收至少证明：

- 无旧 SESSION、manifest 链或 runs 归档时仍能以当前快照启动下一轮并生成页面。
- 研究过程中正式快照不受暂存更新影响；失败、未选及未完成项不覆盖有效记录。
- 基线漂移拒绝合并，重复应用不重复追加，写入中断可恢复且不暴露混合版本。
- 合并后当前证据引用有效；移除已合并过程副本后仍可校验、生成。

`npm run check` 校验正式快照与所有派生输出，历史 runs／manifest 不再是校验条件。本轮 WORK 检查点由 stage／plan 验证；中断、冲突和幂等路径通过隔离临时验证检查，不维护合成 testcase。

同时人工核对 README 结果入口与来源链接是否完整、所链接产物是否存在、证据文件是否存在、
来源版本是否可追溯、报告与数据是否一致、失败是否被正确保留，
以及待复核结论是否仍被误写为当前版本的验证结果。
核对详情、四标签短评与推荐是否一致，推荐是否区分安装与探索试用，周推荐是否写明日期和范围；
不得将源码级候选包装成已验收安装推荐。
评分还需核对两轴分项与总分、理由与参照、版本和依赖有效性；确保推荐按有效均分排序、缺失项不当0，且读者Markdown没有评分泄漏。
洞察还需核对作者主张与研究者识别的贡献是否分开、参照和归属是否明确、质疑是否触及核心贡献、假设是否能追溯到发现，
是否区分已有贡献／待验证假设／探索性设想、是否避免强凑创新，以及事实与解释是否分开、比较条件是否可比、是否检查反例、影响是否有适用条件，
以及下一步验证能否支持或推翻判断。还须检查安装依赖是否被误当效果保证、后台和异常成本是否遗漏、
成本单位是否对应合格任务，以及现金与人工时间是否被无依据混算。数据校验通过不代替这些语义检查。
自动校验覆盖当前快照结构、身份、分析绑定、嵌入证据摘要及生成一致性；本轮暂存与提交另验证基线、检查点与幂等。它不自动验证报告叙述、证据内容真实性或实际宿主效果。

将 README 入口更新与本次档案、运行清单、当前详情及发布输入作为 Git 内可检查的交付组合；本地观察批次、证据和报告用于恢复与深度审计。
提交／推送／PR 操作沿用用户授权和根 `AGENTS.md` 的仓库约束；本地校验与远端 CI 结果分别报告。
面向用户的交付说明给出结果入口、关键变化、验证结果及未完成边界，不要求用户从过程消息中拼接结论。

## 分类页目录与 META

分类页顶部先给插件目录，每项为“插件名＋一句话用途”，链接本页稳定组件锚点。
下方按业务分类展示插件名、META、用途／亮点／思考／建议，插件标题作为详情入口，不单列“详细分析”行，不单独展示“研究深度：源码级”。
证据与运行边界仍由详情和推荐说明，不能因隐藏标签而升级结论。

GitHub META 使用 `npm run capture:meta -- OWNER/REPO --out data/runs/<round>/snapshots/<plugin-slug>/META.json` 采集，
通过发布输入 metadata 映射稳定插件 ID 到快照。README、分类条目和详情页摘要下方统一按 README 样式展示 GitHub Star、npm 下载量、最后更新及更新标记：三项均使用同一组 Shields 徽章、相同顺序和链接，不在分类或详情页另附推送日期文本。未关闭／已关闭 Issue 累计量、近30天新建／关闭／更新量在详情“活跃度”中分成累计与近30天两组静态badge，使用中性灰色，不以颜色暗示质量；每枚链接对应GitHub Issue筛选，保留统计日期。未知值显示“暂未获取”，已知0正常显示0；不显示创新评分。
Issue 搜索强制排除 PR；近期关闭指当前已关闭且 closed_at 落在窗口内的 Issue 数，不能等同于解决数或完整关闭事件数。
累计量是查询当下状态；近期更新包含创建、关闭及其他更新，几个数字不可相加当独立问题数。
失败或不完整结果保存错误并展示“暂未获取”，不能写成0。仓库级 META 不冒充子插件独立活跃度。

相对推送时间按 Asia/Shanghai 的日历日显示今天／昨天／前天／N天前；30天起按30天一月、365天起按365天一年近似。
相对时间以 META 的 captured_at 为准；精确推送日期保留在 META 数据中，README 与分类页顶部统一标注页面更新时间（北京时间）。
不在每个插件下重复采集时间、相对时间口径或排除 PR 的说明；精确时间和口径保存在快照及本规范中。
无需部署 JS 服务，快照和生成输出可重复校验。Star和Issue处理量只作背景，不代替可靠性或采用判断。

## 单插件工程画像

详细分析增加代码规模、能力清单、代码评价及可借鉴处。使用研究规范的统计口径，不在分类短评中堆砌明细。
统计结果保存 `data/runs/<round>/snapshots/<plugin-slug>/INVENTORY.json`，源码证据可通过现有 artifact 字段引用，不改 catalog 字段。

固定提交的完整组件统计：

```sh
npm run inventory:plugin -- --root /path/to/readonly-checkout --ref <commit> --component <component-path> --out data/runs/<round>/snapshots/<plugin-slug>/INVENTORY.json
```

仅有已采集的源码快照时：

```sh
npm run inventory:plugin -- --snapshot data/runs/<round>/snapshots/<plugin-slug>/SOURCE.json --component <component-path> --out data/runs/<round>/snapshots/<plugin-slug>/INVENTORY.json
```

后者必须注明抽读子集，不能当作完整组件统计。根组件省略 component；必要共享目录单独统计，不重复相加。
底层 CLI 可用 `npm run loc -- --format json --details <path>`，正式交付优先用封装以固定范围和排除口径。

详情分别呈现 Markdown 行数／字数，各 JS／TS 扩展名行数，以及生产／测试／示例范围、统计版本、工具版本和排除项。
列正式 Skill 与 Agent／Preset 定义的人工确认结果及用途；保留脚本静态候选和未解析点，未知不填0。
工具、命令、后台／UI、依赖和数据副作用同样区分静态声明与实际挂载；不得把角色数、实例数当Agent定义数。
代码评价和可借鉴处引用具体源文件与证据，解释采用与复用的意义。现有历史详情不因增加格式要求而重写，后续新分析执行。

CI 校验当前研究档案、运行清单和生成结果一致性；本地 runs 存在时 `npm run check` 额外校验会话检查点。不维护 testcase，也不声称自动确认所有能力注册或代码质量。

### Star 与 npm 下载量

GitHub Star 显示为带仓库链接的 Shields 徽章（GitHub 标志、GitHub ★ 标签与数字）；确认存在对应 npm 包时，显示带 npm 包页链接的 Shields 徽章（npm 标志、npm 30d 标签及下载数）。
徽章用 img.shields.io/static/v1 的 flat 样式，由快照数值生成；不使用 GitHub camo 缓存 URL，也不改成随时间漂移的实时下载数。
数字缺失用灰色“暂未获取”徽章，alt 文本采用同样的 GitHub ★／npm 30d 标签与数字，保留计量含义；原始数字、日期与采集时间仍保存在数据中。
未发布 npm 包或包名未核实时不展示下载项，不能从仓库名猜包名；多组件仓库按已核实的插件 package.json 分别对应。
命令增加 `--npm <exact-package-name>`，包名可含 scope。抓取失败显示“暂未获取”，而非0；返回0才显示0。

下载量取 npm 官方 downloads point API 的最近30个完整 UTC 日期，截止采集日前一天，首尾日期均包含。
保存 package、精确窗口、下载数、来源 URL、采集时间与错误；读者页不逐项展示采集说明，
GitHub 与 npm 的独立时间保留在数据中，README 与分类页顶部显示最新采集日期，独立时间与窗口仍保存在快照中。npm 下载数包含自动化和重复安装，不等于用户数或活跃用户。

## 每日 META 刷新

`npm run refresh:meta` 读取发布输入指向的运行清单完成列表，逐个按仓库地址采集 GitHub META；未选候选不触发采集，
只使用前轮已确认的 npm 包名更新下载量，在本地当前轮次 snapshots/meta-refresh/<时间>/<plugin-slug>/ 保存新快照，更新 Git 内稳定 META 副本并重生成 README／分类页及相对时间。
没有已确认包名时跳过 npm，不能猜测；自动任务不做列表发现、单插件研究或目标代码执行。

对比清单固定研究提交与仓库默认分支当前提交，在组件范围检查 JS／TS 脚本变更（含删除和移出路径）；
变化保存 code_update，页面标“脚本有更新，待重新洞察”，推荐摘要提示待复核。仅文档／其他组件变化不标脚本更新。
比较失败、分支回退／分叉或文件列表达到300上限时记录未知，不误写无变化。共享目录、依赖、Skill和外部服务变化仍需研究者另查。
自动任务不改 catalog findings、研究深度或完成检查点，旧研究版本持续保留；重新洞察后以新会话基线清除变化标记。

GitHub Actions 每天北京时间08:30及手动触发，复用未合并的 META PR，普通提交和推送，不强推、不自动合并 main。
合并冲突则停止，由维护者处理。机器人 PR 后显式 dispatch CI，确保 Repository checks 检查对应分支头。
默认 GITHUB_TOKEN 需要 contents／pull-requests／actions 写权限，并须允许 Actions 创建 PR；
工作流合入默认分支后定时执行才生效。实际时间可能受 GitHub 调度延迟影响。

## 详细分析展示层

生成器以检查点绑定的研究原稿为输入，使用 DETAIL／ISSUES 模板生成 `data/plugins/<plugin-slug>/INSIGHT.md`，
将原稿“固定范围与依据”转换为“版本”，该节仅展示固定提交与链接，不显示组件 ID、路径、轮次、核查时间及材料清单；完整依据保留在当前快照引用的正式分析和证据中。
追加“活跃度”区块，展示最新 Issue 统计。README和分类页链接此展示页；原稿不改写，不改变证据、结论或检查点摘要。
目标流程的原稿在本轮 insights 暂存，合并时落入当前快照的正式分析位置；展示页从正式分析生成，仍位于稳定插件目录。生成器从快照内 reports 读取正式原文，清理已合并 runs 不影响生成；展示页不是第二份人工研究真相源。
展示页与README一起生成并通过 --check 校验，META刷新也更新展示页。Issue数据注明日期，失败显示暂未获取；页面不重复“Issue 不含 PR”的口径说明，也不输出生成器注释。

项目头图使用严肃、偏技术的 PNG，位于 `assets/dsh-plugin-insight-banner.png`，标题统一为 DSH Plugin Insight。

init 可带最大研究插件数；完整清单仍保留，报告分别注明清单总数、所选数、完成数、受阻数和未选数。达到上限仅表示所选范围完成，不代表完整清单全部研究完成；新增、更新、删除共用额度，未变已有项不占额度，更新优先、新项补足；具体选择与恢复语义见数据契约。

读者页的用途／亮点／思考／建议标签采用 `**标签**：正文` 加粗，由 SHORT-ITEM 模板统一生成，避免中文冒号与 Markdown 星号边界导致原样显示。检查点绑定的研究原稿保留原文，展示层转换标签。

历史研究原稿的“关键质疑”标签由展示层兼容读取并显示为“思考”；新研究使用“思考”，同一原稿同时出现两者视为重复标签并拒绝生成。

README 的最后更新使用与 GitHub／npm 同风格的 Shields 徽章，带 GitHub 图标、最后更新标签和相对时间，并链接仓库提交记录；不展示括号中的具体日期。最新区块同样使用此徽章。分类页保留相对时间与具体日期，原始时间仍保存于 META 快照。

npm 采集同时保存 publication 的首次发布时间、采集时间、注册表来源和错误；下载数与发布时间独立失败，不互相用0或入档时间补足。每日 META 刷新一并更新这些字段。

INSIGHT 标题下用 `>` 展示项目自己的功能简介：依据固定版本 README／package 描述，人工归纳为一至两句中文，最多80个 Unicode 字符（含标点和空格），不机械截断，不混入亮点、质疑、收益判断或安装建议。发布输入 summaries 按插件 ID 保存 text、source_url、revision；生成器核对字数、单行及源码版本，缺失时补齐后再生成。引用块为功能摘要而非逐字引文，来源在结构化输入中保留。

INSIGHT 展示页保留工程统计表，不展示 sloc／TypeScript 版本、通用计数口径及生成／第三方代码辨认的两段说明；完整口径保留在研究原稿、统计 JSON 与研究规范。具体影响采用判断的统计限制仍在相应分析中说明。

INSIGHT 能力清单只列已人工确认存在的正向条目，未发现／未确认的项不展示，不写0或“无某能力”。发布输入 capabilities 按稳定 ID 保存 revision 与 items；静态候选及否定说明仍在原稿、统计 JSON 留存，不能据此自动补数。无已确认条目时该部分留空。

INSIGHT 中代码评价与可借鉴内容的章节标题统一为“工程亮点”；历史原稿标题由展示层转换，保留原始依据。

使用建议用日常语言说明适合谁、先检查什么、做不到什么，避免“采用判断”“最小验证”等抽象表述。历史原稿的建议可通过发布输入 advice（revision、text）润色；必须绑定同一固定提交，保留原意、风险与证据边界，不添加未经验证的结论。

详情的核查说明使用简短 `-` 列表，分别交代已检查材料、未完成验证和证据限制；避免在同一长段中堆叠。展示层通过 BOUNDARIES 模板精简已识别的历史固定文案，其他具体边界原样保留为列表，不推断验证状态。
